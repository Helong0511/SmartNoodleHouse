### 6.1 检测与识别分离

明确区分：

1. 检测画面中是否存在人脸。
2. 判断人脸图像质量是否满足要求。
3. 提取人脸特征。
4. 在有权限的会员特征库中匹配。
5. 判断身份是否足够可靠。
6. 根据业务规则触发迎宾。

禁止将人形检测、普通目标检测或人脸检测直接当成会员身份识别成功。

### 6.2 人脸质量判断

检查并适当实现：

- 最小有效人脸尺寸。
- 模糊度检查。
- 过暗或过曝检查。
- 关键点及对齐质量。
- 侧脸、遮挡及运动模糊处理。
- 同一人脸连续出现时的跟踪。
- 多人同时出现时的独立识别状态。

质量不足时应跳过匹配或延迟确认，不得强行给出身份。

阈值应可配置并有合理的校验范围，不得硬编码为某个未经验证的万能值。

### 6.3 相似度阈值和误识别

重点检查现有的 `face_match_threshold` 及类似配置。

特别检查是否存在类似：

`best_sim >= threshold + 0.04`

即可跳过二次确认的快速确认路径。

不要因为它能提高速度就默认保留。应先评估其误识别风险，再选择以下方案之一：

- 删除快速确认。
- 仅在经过验证的高质量场景中启用。
- 增加更严格的跨帧证据。
- 根据验证集调整阈值和确认策略。

不得在没有数据支持的情况下随意设置推荐阈值。

建立独立验证集，统计：

- 误接受率。
- 错误识别次数。
- 漏识率。
- 无法识别率。
- 不同距离及光照下的结果。
- 不同人脸尺寸下的结果。
- 多人场景下的结果。

必须说明阈值、模型版本和测试集之间的关系。

### 6.4 跨帧确认

实现或验证：

- 连续多帧证据。
- 同一跟踪目标的稳定关联。
- 相同会员候选的连续一致性。
- 证据不足时重置候选。
- 候选切换时防止串用上一个会员的身份。
- 识别状态在断线、重连和摄像头重启后正确重置。
- 快速经过时不无限保留旧候选。
- 不同摄像头之间隔离跟踪状态。

多帧确认应当使用真实时间和跟踪目标进行判断，而不是仅仅累计相同会员的次数。

### 6.5 防止错配会员姓名

欢迎语必须来自最终确认的会员对象，不能来自过期候选。

确认身份时，必须确保：

- 会员记录仍然存在。
- 会员处于允许参与人脸识别的状态。
- 当前门店有权使用该会员记录。
- 授权状态符合要求。
- 使用的是该会员当前有效的姓名或称呼。
- 没有将旧帧中的会员身份用于新帧。

对数据库中缺失、停用、撤回授权或数据不一致的会员，应安全地拒绝个性化播报。

要求：

1. 没有满足业务及法律要求的授权时，不得将人脸注册为可用于识别的会员特征。
2. 授权撤回后，立即阻止该特征参与后续匹配。
3. 失效缓存必须清除或失效。
4. 已撤回授权的用户不得通过备用路径重新命中。
5. 提供可审计的数据删除或去标识化流程。
6. 对陌生访客抓拍实行明确的启用开关。
7. 保存期限必须可配置，并由后台任务实际执行清理。
8. 记录访问和删除操作，但不得在日志中输出人脸特征向量。
9. 限制图片、特征数据及识别日志的访问权限。
10. 对数据导出、备份和迁移制定相应保护措施。

不要将抓拍保存、会员注册和会员授权混为一谈。

对相关法律要求存在不确定性时，在文档中标明需要由项目负责人确认的事项，不得凭空声称已经满足全部法律要求。

## 八、第五阶段：会员迎宾业务逻辑

重点检查 `WelcomeService.try_welcome()` 和所有调用方。

### 8.1 触发条件

只有在以下条件满足时才能触发会员个性化欢迎：

- 人脸检测有效。
- 识别证据达到配置要求。
- 身份匹配可靠。
- 会员状态有效。
- 授权有效。
- 当前门店及设备权限有效。
- 当前会员尚未触发相应范围内的冷却限制。
- 欢迎语内容合法且不为空。

任何条件不满足，都不能直接使用候选会员姓名播报。

### 8.2 幂等和去重

建立明确的任务唯一标识。

同一会员在同一门店的重复识别，不应因为两个摄像头、两个 Worker 或两个后端进程同时执行而重复播报。

需要评估去重键应包含哪些字段，例如：

- 门店 ID。
- 会员 ID。
- 迎宾事件或访问会话 ID。
- 业务时间窗口。

不要只依赖 Python 进程内字典实现全局去重。

如果 Redis 可用，应采用原子操作实现必要的分布式去重；若 Redis 不可用，应明确回退行为及一致性限制。

### 8.3 冷却与失败恢复

冷却时间应当可配置。

必须区分：

- 已经识别并成功提交任务。
- 已经提交但任务未开始。
- TTS 合成失败。
- 设备认证失败。
- 对讲通道打开失败。
- 音频推送失败。
- 播放结果无法确认。

不要在无法恢复的错误中无限重试。

如果任务入队失败，不应让顾客在很长时间内被永久冷却。应采用合理的状态回滚或短暂失败冷却，并防止并发竞争。

## 九、第六阶段：海康 ISAPI 对讲全面审计

重点审查 `hikvision_audio.py` 以及所有实际调用它的代码。

### 9.1 设备能力探测

检查：

- 认证方式是否正确。
- 是否支持 Digest 认证。
- 请求地址和端口是否正确。
- 对讲能力查询接口是否匹配实际设备文档。
- 音频编码探测是否真实完成。
- 编码缓存是否存在过期或错误复用。
- 设备账号或密码变更后是否清理客户端缓存。
- HTTP 与 HTTPS 是否使用正确的传输实现。
- 请求超时、连接超时和读取超时是否明确。
- 响应状态码及设备返回的错误信息是否被正确处理。

不得将默认音频编码标记为已经探测成功。

### 9.2 首次播报

重点检查当前编码缓存未命中时是否存在以下风险：

- 直接使用默认 G.711 编码。
- 后台异步探测实际编码。
- 在实际编码未知时已经开始首次推流。

如果存在上述逻辑，应优先修改为：

1. 摄像头配置完成后进行能力探测。
2. 探测结果存入带版本或有效期的缓存。
3. 首次播报前验证设备能力。
4. 未验证时在超时范围内探测。
5. 探测失败则返回明确错误。
6. 不得将猜测值当作真实设备能力。
7. 固件或配置变化后支持重新探测。

### 9.3 HTTP 客户端生命周期

检查是否使用全局或共享 HTTP 客户端。

如果认证信息被客户端缓存，则必须保证：

- 客户端与对应设备配置绑定。
- 密码变更时旧客户端被安全关闭。
- 地址或协议变化时重新创建客户端。
- 多个摄像头不会错误共享认证信息。
- 并发关闭客户端不会影响其他仍在执行的请求。
- 应用关闭时能够释放资源。

### 9.4 音频推送

逐项检查：

- 对讲会话建立顺序。
- 实际请求方法和请求头。
- 音频格式要求。
- WAV 解码。
- 采样率。
- 声道数。
- 位深。
- G.711 A-law 或 μ-law 的正确选择。
- PCM 到 G.711 的转换。
- 数据分块及顺序。
- 音频传输长度。
- 结束标记或会话关闭方式。
- 设备返回码。
- 连接中断。
- 发送超时。
- 尾部音频截断。
- 资源清理。

音频协议必须依据官方文档和实际探测结果实现，不能猜测。

必须将以下结果区分开：

- 设备认证成功。
- 对讲通道打开成功。
- 音频编码验证成功。
- 音频数据发送完成。
- 设备明确确认播放完成。
- 播放结果无法验证。

如果设备没有提供可靠的播放完成确认机制，应明确标记为“播放未验证”，不能声称已确认顾客听到了声音。

### 9.5 音频转换与诊断

为音频处理编写独立测试。

至少测试：

- 合法 WAV。
- 空音频。
- 损坏 WAV。
- 不支持的采样率。
- 单声道和立体声输入。
- 不同位深。
- 编码转换后长度是否正确。
- 超长音频。
- 语音末尾是否完整。
- 无效编码参数。
- 音频转换失败时是否返回可诊断的错误。

所有音频转换应具有明确的输入限制和超时策略。

## 十、第七阶段：中文 TTS 语音合成

重点审计 `tts_worker.py`、`LocalTTS` 以及所有 TTS 实现。

### 10.1 TTS 引擎

确认当前运行环境实际使用哪个引擎。

不要因为 Windows 上有某个语音接口，就假设 Linux 服务器也有相同能力。

必须检查：

- 引擎是否已安装。
- 中文语音是否可用。
- 调用是否有超时。
- 异常时是否会释放资源。
- 输出文件是否真实存在且非空。
- 音频文件格式是否正确。
- 临时文件是否清理。
- 多个任务并发合成时是否发生文件覆盖。
- 中文姓名、特殊字符和空白姓名是否正确处理。

不得使用占位音频冒充合成成功。

### 10.2 欢迎语模板

支持可配置的中文欢迎语，例如：

“欢迎回来，张先生。”

具体称呼必须来自当前已确认的会员资料，不得臆造姓名、性别或称谓。

如果姓名为空、包含不适合播报的内容或无法安全处理，应使用通用欢迎语。

必须支持：

- 通用欢迎语。
- 会员欢迎语。
- 可选会员等级称呼。
- 长度限制。
- 空白和控制字符过滤。
- 文本格式校验。
- 配置预览。
- TTS 试听。
- 音频生成失败提示。

不要把数据库内容直接拼接成任意长度的 TTS 文本。

### 10.3 音频缓存

如果实现 TTS 缓存：

- 缓存键必须包含文本、语音引擎、语音配置及版本。
- 不同会员的个性化文本不得错误复用。
- 临时文件名必须唯一。
- 缓存容量必须有上限。
- 缓存文件应有明确的清理策略。
- 缓存损坏时能够重新生成。
- 不得将缓存文件路径直接暴露给不受信任的请求。

## 十一、第八阶段：播报队列与并发控制

重点检查 Redis、进程内队列、Worker 生命周期及任务状态。

### 11.1 任务状态机

设计明确、可追踪的播报状态。

至少区分：

- QUEUED：等待处理。
- PROCESSING：正在处理。
- SYNTHESIZED：TTS 合成完成。
- CHANNEL_OPENED：对讲通道已打开。
- AUDIO_SENT：音频已发送。
- PLAYBACK_UNVERIFIED：播放结果未验证。
- SUCCEEDED：只有满足项目定义的成功条件时才可使用。
- FAILED：任务失败。
- EXPIRED：任务已过期。
- CANCELLED：任务被取消。

如现有系统已有类似状态，应兼容现有结构，避免无必要的数据库重构。

状态更新必须有明确的时间戳、错误码和安全的错误摘要。

### 11.2 队列规则

实现或验证：

- 有界队列。
- 队列满时的明确处理。
- 任务超时。
- 过期任务清理。
- 有限重试次数。
- 失败退避。
- Worker 异常恢复。
- 优雅停止。
- 进程重启后的状态恢复。
- 多 Worker 并发安全。
- 防止同一任务被重复消费。

不要允许旧欢迎语在顾客离开很久后才播出。

### 11.3 播报优先级

建议：

1. 已确认的会员个性化欢迎语优先。
2. 通用欢迎语可以合并、抑制或丢弃。
3. 不得将新任务直接覆盖正在播放的任务。
4. 不得把一个会员的姓名错误地拼接到另一个会员的任务中。
5. 播报中断时记录原因。
6. 多摄像头共享扬声器或设备时，必须明确资源锁定规则。

如果一个摄像头对应一个独立扬声器，可按设备独立调度；如果多个识别源共享同一个扬声器，则必须实现设备级播放互斥。

### 11.4 Redis 故障

检查 Redis 断开后的降级策略。

必须明确：

- 哪些功能可以继续。
- 哪些功能需要停止。
- 内存队列的容量。
- 多进程情况下的去重能力。
- 恢复 Redis 后是否清理过期状态。
- 是否可能发生任务重复提交。

不得将内存回退描述为具备分布式一致性。

## 十二、第九阶段：前端摄像头管理界面

检查 `frontend/src/views/Cameras.vue` 以及关联组件和 API。

必须确保前端真实反映后端状态，而不是仅根据按钮点击就显示成功。

建议完善：

### 12.1 摄像头状态

显示：

- 摄像头名称。
- 所属门店。
- 在线状态。
- 最近有效帧时间。
- 视频帧率。
- 识别 Worker 状态。
- 人脸模型状态。
- 音频能力探测状态。
- 对讲认证状态。
- 最近一次播报结果。
- 最近错误原因。
- 最后成功连接时间。

### 12.2 测试操作

提供独立操作：

- 测试视频连接。
- 预览视频。
- 测试人脸检测。
- 测试会员匹配。
- 探测音频能力。
- 测试对讲通道。
- 电脑扬声器试听。
- 摄像头扬声器试听。
- 查看最近播报日志。
- 重新连接摄像头。

每个操作必须显示真实的后端响应。

危险操作需要确认，并遵循现有权限控制。

### 12.3 错误显示

不要只显示“操作失败”。

应在不泄露密码、内部凭据和敏感数据的前提下，显示可理解的错误分类：

- 设备无法连接。
- RTSP 认证失败。
- ISAPI 认证失败。
- 对讲能力不支持或未探测。
- 音频编码不匹配。
- TTS 引擎不可用。
- 播报队列已满。
- 任务超时。
- 播放结果未验证。

## 十三、第十阶段：后端 API、安全及数据库

### 13.1 API

逐一检查摄像头管理、测试、启动、停止、预览和诊断 API。

必须验证：

- 身份认证。
- 权限校验。
- 门店级数据隔离。
- 输入验证。
- 请求超时。
- 异常处理。
- 并发启动和停止。
- 重复请求。
- 资源释放。
- 错误响应格式。

禁止未授权用户调用接口获取实时视频、触发摄像头扬声器、读取会员身份或下载人脸图片。

### 13.2 SSRF 与网络访问

摄像头地址通常由管理员配置。检查是否存在通过修改地址访问任意内部服务的风险。

应限制允许的目标地址和端口，避免摄像头探测接口被利用来访问云元数据地址、数据库、Redis 或其他不允许访问的内部服务。

兼容合法的内网摄像头部署，不要简单地禁止所有私有 IP。

### 13.3 凭据安全

检查：

- 摄像头密码是否明文保存。
- 加密密钥是否写死在源代码中。
- 日志是否暴露密码。
- API 是否返回完整 RTSP URL。
- 异常堆栈是否包含凭据。
- 前端是否将密码存入不必要的持久化存储。
- 修改密码时旧缓存是否失效。
- 数据库备份是否保护敏感配置。

如果当前加密实现存在问题，应使用现有安全架构进行最小范围修复，不得凭空引入一个未经设计的密钥管理系统。

### 13.4 数据库兼容

检查会员、摄像头、迎宾记录和播报任务的表结构。

任何新增字段、索引或约束都必须：

- 提供兼容迁移。
- 说明默认值。
- 考虑已有数据。
- 避免长时间锁表。
- 支持回滚或给出恢复方案。
- 检查查询性能。
- 避免将大音频文件直接写入普通业务表，除非现有架构明确要求。

优先复用现有字段和数据模型，只有确有必要时才扩展。

## 十四、第十一阶段：日志、指标及故障诊断

建立统一的诊断链路，使一条迎宾任务可以从人脸识别追踪到最终音频发送。

建议为每次任务分配 `event_id` 或 `task_id`。

关联以下信息：

- 门店 ID。
- 摄像头 ID。
- 会员 ID（使用受控标识，不在普通日志中暴露不必要的个人信息）。
- 人脸匹配结果及必要的统计信息。
- 识别耗时。
- 入队时间。
- TTS 开始及结束时间。
- 对讲连接时间。
- 音频发送时间。
- 最终任务状态。
- 失败分类。

不要记录完整人脸特征、明文密码、未经必要脱敏的个人信息或完整敏感 URL。

建议增加以下指标：

- 摄像头在线率。
- 有效帧率。
- 人脸检测次数。
- 可靠匹配次数。
- 无法匹配次数。
- 识别耗时分布。
- 误识别和漏识别验证结果。
- TTS 成功率。
- 对讲连接成功率。
- 音频发送成功率。
- 未验证播放的任务数。
- 队列长度。
- 任务失败率。
- 任务过期数。
- 端到端延迟。

日志必须支持按时间、门店、摄像头和任务 ID 查询。

## 十五、第十二阶段：自动化测试

必须增加或完善测试，禁止仅靠手动观察代码判断完成。

### 15.1 单元测试

至少覆盖：

- 人脸匹配阈值。
- 低质量人脸。
- 跨帧确认。
- 候选切换。
- 会员状态变化。
- 授权撤回。
- 迎宾冷却。
- 并发去重。
- 队列满。
- 任务过期。
- TTS 失败。
- 无效音频。
- 编码探测失败。
- 摄像头认证失败。
- 网络超时。
- 重试上限。
- 缓存失效。
- 资源清理。

### 15.2 集成测试

测试：

1. 模拟摄像头返回视频帧。
2. 模拟识别出已授权会员。
3. 生成欢迎语。
4. 创建播报任务。
5. 模拟 TTS 成功。
6. 模拟海康对讲成功。
7. 验证任务状态和日志。
8. 模拟每个环节失败。
9. 验证错误能够准确传播。
10. 验证失败后不会无限重试或错误标记成功。

外部设备应使用明确的模拟适配器或 Mock，不要在普通自动化测试中向真实摄像头发送未授权的音频。

### 15.3 并发测试

覆盖：

- 多线程同时识别同一会员。
- 多 Worker 同时提交迎宾。
- 多摄像头识别同一会员。
- Redis 短暂不可用。
- 队列达到容量上限。
- TTS 任务耗时异常。
- 播报设备正在被占用。
- 后端停止时仍有任务运行。

验证没有重复任务、状态竞争、死锁、线程泄漏或无限积压。

### 15.4 性能测试

至少记录：

- 视频处理帧率。
- 人脸检测耗时。
- 特征匹配耗时。
- 迎宾任务排队延迟。
- TTS 合成耗时。
- 音频发送耗时。
- 总体延迟分布。
- 内存和 CPU 使用。
- 长时间运行后的资源变化。

性能目标应结合实际硬件确定。不要在没有基准数据时编造 QPS 或准确率。

## 十六、第十三阶段：真实设备验收
