# 2. P0：敏感文件与密钥治理

## 2.1 盘点 Git 跟踪文件

重点检查：

```bash
git ls-files uploads
git ls-files | grep -Ei '(^|/)(\.env|.*\.pem|.*\.key|.*\.p12|.*\.pfx|.*credential.*|.*secret.*|.*开户.*|.*身份证.*|.*银行卡.*|.*face.*|.*snapshot.*)'
git log --all --name-status -- uploads
git log --all --name-status -- '*.pem' '*.key' '*.p12' '*.pfx' '.env*'
```

使用 secret scanner（例如 gitleaks，版本固定并记录）扫描当前文件和 Git 历史。扫描输出必须脱敏，报告不得复制真实密钥。

## 2.2 敏感文件处置

若确认存在不应公开的开户资料或顾客文件：

1. 先记录文件路径、Git blob、提交历史和暴露范围，不在报告中展示内容。
2. 从当前仓库删除并增加忽略规则。
3. 使用经过审核的 Git 历史清理方案移除历史对象；先备份仓库、确认协作者和分支策略。
4. 历史重写需要负责人批准；不得擅自强推覆盖他人工作。
5. 对已经公开的真实凭证执行轮换/吊销；文件删除不等于凭证失效。
6. 检查 Fork、Release、Actions artifact、缓存、镜像、备份是否另有副本。
7. 对疑似个人/财务资料按数据泄露流程处理，必要时由资料所有者联系相关机构。

## 2.3 上传目录规范

- 运行时上传内容放在仓库外的持久化目录或受控对象存储。
- Git 仅保留空目录占位说明或示例文件。
- 对图片、证件、顾客人脸、摄像头截图、支付凭证实施私有存储。
- 上传 API 必须校验登录、角色、门店、大小、扩展名、MIME、文件签名、图片解码、文件名随机化。
- 禁止路径穿越、双扩展名、SVG/HTML 脚本注入、压缩炸弹、超大图片和恶意文件。
- 文件下载必须经过授权，不能暴露可枚举的静态路径。
- 日志仅记录文件 ID、操作者、门店、时间和操作结果，不记录文件内容或敏感 URL。

## 2.4 环境变量和密钥

- 提供 `.env.example`，只包含占位符。
- 启动时校验必需密钥是否存在、长度/格式是否合理；生产环境拒绝弱默认值。
- 密钥从环境变量或受控 Secret Manager 注入，不写入源码、镜像、前端构建变量或小程序包。
- 区分开发、测试、预发布、生产凭证。
- 对 JWT、数据库、Redis、微信/支付宝、外卖平台、摄像头凭证设置轮换方案。
- 禁止把私钥、公钥混淆；公钥可以公开不代表私钥可以提交。
- 生成密钥扫描 CI，发现真实凭证立即失败。

验收：
- 当前仓库和 Git 历史扫描无未处置的真实密钥/敏感资料；
- 上传数据不再被 Git 跟踪；
- 生产凭证已按暴露风险轮换；
- 新增 secret scan CI；
- 日志脱敏测试通过。

# 5. P1：微信 / 支付宝小程序身份与用户体验

## 5.1 身份模型

保持“首次扫码/授权可创建平台侧匿名会员身份”的合理设计，但要明确：

- 微信身份主键为平台作用域内的 OpenID，UnionID 仅在满足平台条件时作为关联依据；
- 支付宝身份使用对应应用作用域的 user ID；
- 微信与支付宝默认是两个外部身份，不可仅凭昵称或头像合并；
- 跨平台统一会员必须通过经过验证的手机号或明确的账号关联流程；
- 匿名/未完善资料顾客可以点餐，不得强迫无必要注册；
- 用户授权、会员资料完善、营销授权分开记录；
- 用户拒绝头像/昵称授权不应阻断基本点餐；
- 顾客身份创建必须幂等，重复登录不产生重复会员；
- 解绑、注销、手机号变更和平台授权失效有完整流程。

## 5.2 双端统一业务契约

对微信与支付宝小程序建立共同业务层/共享契约，平台差异只留在 adapter：

- login；
- token refresh；
- customer profile；
- cart；
- price calculation；
- coupon validation；
- order create；
- payment request；
- payment result query；
- cancel；
- refund status；
- scan/store binding；
- upload；
- location/permission；
- error mapping。

不要强行把两个平台的原生 API 写成完全一样；应统一业务输入输出，平台 adapter 负责转换。

## 5.3 扫码与门店绑定

- 二维码使用服务端签名或不可伪造的随机 token；
- token 绑定活动/门店/有效期/用途；
- 微信和支付宝使用各自可识别的码入口，但解析后落入统一业务协议；
- 不得把明文可篡改 `store_id` 当作授权凭据；
- 校验门店状态、活动有效期、适用范围和重复使用策略；
- 门店二维码过期、门店停用、活动不参与时给出可理解提示；
- 记录扫码来源、平台、门店、活动和必要的防刷信息，遵循最小化原则。

## 5.4 双端测试

同一组业务场景分别在微信和支付宝验证：

- 首次授权；
- 老用户登录；
- 授权取消；
- token 过期；
- 手机号绑定；
- 跨平台账号关联；
- 门店扫码；
- 价格和优惠券；
- 创建订单；
- 支付成功/取消/超时；
- 重复提交；
- 退款；
- 顾客资料删除/解绑。

要求核心价格、订单和权限业务结果一致。

# 6. P1：支付、退款和财务一致性

支付是最高风险业务之一，必须先画出现有状态机，再改代码。不得绕过渠道官方协议。

## 6.1 微信支付

检查并完善：

- API v3 请求签名；
- 平台证书/公钥序列号选择；
- 回调签名原文、时间戳、nonce、serial、signature；
- 平台证书轮换；
- 回调 AES-GCM 解密；
- AppID、商户号、子商户号、币种、金额、商户订单号、微信交易号校验；
- 回调时间窗口和重放防护；
- 退款回调；
- 证书更新和失效处理；
- 失败时返回符合官方要求的响应。

`Wechatpay-Serial` 必须参与平台证书/公钥的正确选择与校验；不能只读取不使用。公钥模式和证书模式按实际配置明确区分，禁止混用。

## 6.2 支付宝

检查：

- RSA2 签名；
- 应用公钥/支付宝公钥用途；
- app_id；
- seller_id；
- out_trade_no；
- trade_no；
- total_amount；
- trade_status；
- notify_id/回调重放；
- 退款通知和主动查单；
- 金额精度与币种；
- 回调原始参数的规范验证。

## 6.3 支付金额和订单归属

金额统一使用 Decimal/整数分，不得使用 float。服务端重新计算商品、规格、加料、折扣、配送费、包装费、优惠券、会员折扣和应付金额。客户端金额只作为展示值。

校验：

- 支付金额等于服务端应付金额；
- 币种匹配；
- 订单归属和门店匹配；
- 支付单属于对应订单；
- 同一个支付单不能支付其他订单；
- 不接受低金额或其他商户的回调；
- 分笔支付累计不超过应付金额；
- 并发支付只能有一个有效资金结果；
- 超额支付必须进入人工对账/退款流程，不能静默忽略。

## 6.4 幂等和事务

设计并测试：

- create payment 幂等键；
- notify 唯一键；
- channel transaction ID 唯一约束；
- payment/order 行锁；
- 数据库事务；
- outbox 事件；
- 回调处理结果持久化；
- Redis 不可用时的数据库兜底；
- 重复回调；
- 回调成功但本地提交失败；
- 渠道成功但前端超时；
- 查单补偿；
- 迟到成功；
- 订单取消与支付竞态；
- 多渠道同时付款；
- 重复退款和部分退款。

Redis 不能成为唯一幂等保障；关键唯一性必须由数据库约束兜底。

## 6.5 财务账本与对账

确认项目是否有独立、不可随意覆盖的支付/退款流水账本。若没有，设计兼容性方案：

- payment transaction；
- refund transaction；
- channel transaction ID；
- 金额、币种；
- 门店；
- 订单；
- 支付渠道；
- 成功时间；
- 对账状态；
- 操作人/来源；
- 原始通知的安全摘要（不得保存不必要敏感信息）。

建立定时对账：本地成功而渠道失败、本地失败而渠道成功、金额不一致、退款不一致、重复交易。差异进入人工处理队列，不自动篡改历史流水。

## 6.6 必须通过的支付测试

1. 正常支付；
2. 签名错误；
3. 证书序列号错误；
4. AppID 错误；
5. 商户号错误；
6. 金额少一分/多一分；
7. 币种错误；
8. 订单不存在；
9. 支付单不属于该订单；
10. 重复回调 100 次；
11. 并发回调；
12. 微信与支付宝并发支付；
13. 前端超时但渠道成功；
14. 回调到达时订单已取消；
15. 部分退款；
16. 全额退款；
17. 重复退款回调；
18. Redis 故障；
19. MySQL 提交失败；
20. 渠道主动查单补偿。

所有测试使用沙箱/模拟签名密钥，不使用真实生产密钥或真实顾客支付。

# 7. P1：订单状态机、库存、菜品和规格

## 7.1 订单状态机

- 列出所有订单状态和合法迁移；
- 状态迁移集中在领域服务，不允许 API 任意赋值；
- 每次迁移校验操作者、门店、当前状态和业务前置条件；
- 状态迁移记录 before/after、原因、来源、操作者和时间；
- 禁止终态订单被普通操作回退；
- 支付、取消、退款、制作、出餐、完成之间定义竞态策略；
- API 重试不能重复触发副作用。

为所有合法/非法迁移建立表驱动测试。

## 7.2 库存一致性

库存至少区分：

- 品牌默认餐品；
- 门店餐品；
- 规格；
- 加料/配料（若独立计库存）；
- 外卖渠道可售库存；
- 实际库存；
- 预占库存（如现有设计支持）；
- 安全库存；
- 不限库存。

检查扣减是否使用原子 SQL/行锁/条件更新。禁止先读库存、在应用层判断后无锁写回。

并发测试：
- 库存 1，100 个并发下单；
- 库存 5，多个 Worker 并发扣减；
- 同订单重复支付通知；
- 同订单重复取消；
- 退款回库重复执行；
- 取消与支付同时发生；
- 两个门店同菜品；
- 规格/加料库存不足；
- 无限库存转有限库存；
- 补货与外卖推送并发。

数据库库存不得出现负数；每一次扣减/回滚必须能追溯到业务事件。

## 7.3 菜品与价格

- 价格统一 Decimal；
- 规格、加料、套餐、优惠、会员折扣计算在服务端；
- 下单保存价格快照，菜单改价不改变历史订单；
- 下架餐品不能新下单，已支付订单按既定规则处理；
- 门店独立售价、品牌默认价和外卖平台价明确优先级；
- 图片上传与删除安全；
- 菜品、规格、库存、外卖映射关系有唯一约束和审计记录。

# 8. P1：外卖平台、多门店同步与 KDS

## 8.1 平台账号与门店绑定

按美团、饿了么官方开放平台实际协议核对：

- 一个门店是否需要独立平台门店/商户绑定；
- app key、secret、门店 ID、授权 token 的作用域；
- token 刷新；
- webhook 验签；
- 请求签名；
- 请求频率；
- 平台接口版本；
- 菜品、规格、价格、库存、上下架和订单状态接口；
- 失败重试和错误码映射。

不允许假设一个平台账号可自动管理所有门店；必须按真实平台合同/开放平台权限设计映射。

## 8.2 同步架构

建立统一平台 adapter：

- MeituanAdapter；
- ElemeAdapter；
- 统一菜品 DTO；
- 统一规格 DTO；
- 统一库存 DTO；
- 统一订单 DTO；
- 平台特定字段映射。

同步使用 Outbox/任务表：

- 每个事件有唯一 event ID；
- 门店、平台、对象、版本/更新时间；
- 幂等键；
- 重试次数；
- 下次重试时间；
- 错误分类；
- dead-letter 状态；
- 人工重放；
- 同对象乱序保护。

不能让平台接口失败阻塞堂食下单。堂食库存与外卖可售库存之间要有明确的共享/分配策略，不能各渠道各自扣减造成超卖。

## 8.3 KDS

检查：

- 门店隔离；
- 工位/档口分流；
- 订单排序；
- 加料/口味备注；
- 订单拆单/合单；
- 叫号；
- 制作中/待出餐/已出餐；
- 断线重连；
- WebSocket 鉴权；
- 重复事件；
- 网络恢复后的状态补齐；
- 打印机离线和重试；
- 订单取消/退款后厨房提示。

KDS 状态必须以服务端订单状态为准，前端乐观更新失败后能够恢复。

# 9. P1：摄像头、人脸识别和语音播报

## 9.1 活体检测边界

必须区分：

- 人脸检测；
- 人脸比对；
- 随机动作挑战；
- 服务端视觉活体检测；
- 设备/摄像头反欺骗；
- 会员身份认证。

客户端提交 `action_completed=true` 不能证明动作真的发生。默认值必须安全失败，服务端必须验证挑战绑定、有效期、一次性使用和实际证据。

如果当前算法无法做可靠视觉活体检测：
- 不得把它标记为已通过活体；
- 在产品 UI 中明确能力边界；
- 对高风险认证禁用该方式或接入经验证的活体方案；
- 对普通迎宾识别使用多帧一致性、阈值、人工纠错和防误播策略。

## 9.2 人脸数据治理

- 明确采集目的和授权；
- 仅采集必要数据；
- 原始照片和特征模板分开存储；
- 传输和静态加密；
- 密钥与数据分离；
- 按门店/租户限制访问；
- 人脸查询和导出审计；
- 支持撤回授权、删除、过期清理；
- 备份中的删除策略明确；
- 禁止将原始图像或 embedding 写入普通日志；
- 测试数据必须为合成/授权样本。

## 9.3 摄像头 URL / SSRF

- 只允许明确支持的 Scheme；
- 禁止 file、ftp、gopher、data 等非预期 Scheme；
- 拒绝 userinfo、异常端口、混淆 IP、IPv6 绕过；
- DNS 解析后校验所有 A/AAAA 结果；
- 防止 DNS rebinding；
- 连接时绑定/再次校验实际目的地址；
- 限制内网地址范围为明确配置的摄像头网段；
- 禁止云 metadata、localhost、数据库、Redis、控制面等目标；
- 禁止任意重定向；
- 设置连接、读取和总超时；
- 摄像头密码不得出现在日志、异常和前端 URL；
- 测试 IPv4、IPv6、十进制/八进制/十六进制 IP、域名解析变化和重定向。

## 9.4 摄像头生命周期和播报

- 每路摄像头有独立状态和资源上限；
- 断线指数退避重连；
- 单路故障不拖垮其他摄像头；
- 多进程部署不得重复拉起同一摄像头；
- 租约/分布式锁必须有过期和故障恢复；
- 关闭/重启释放线程、句柄、GPU/CPU 资源；
- 人脸连续多帧确认；
- 同一顾客播报冷却时间；
- 识别置信度不足不播报姓名；
- TTS 队列限长、优先级、过期丢弃；
- TTS 失败不得影响订单和支付；
- 电脑扬声器与摄像头扬声器目标定义统一；
- 前端 `pc/camera/both` 与后端契约一致。

# 13. 执行顺序与阶段交付

必须严格按顺序实施：

| 阶段 | 内容 | 交付物 | 放行条件 |
|---|---|---|---|
| 0 | 最新基线与完整盘点 | 仓库清单、基线报告 | 环境可复现 |
| 1 | 敏感文件/密钥治理 | 泄露处置报告、扫描 CI | 无未处置高危暴露 |
| 2 | CI/依赖/编译修复 | CI 全绿报告 | 后端、前端、双小程序构建通过 |
| 3 | 认证/RBAC/门店隔离 | 权限矩阵、IDOR 测试 | 越权测试全通过 |

每个阶段完成后：
1. 展示变更文件清单；

6. 更新问题台账；
7. 只有通过阶段门禁才进入下一阶段。

# 17. 开始执行时的第一条命令

先不要修改代码。先执行：

```bash
git status --short --branch
git log -1 --oneline
git remote -v
```

然后读取项目指引和 CI 配置，确认最新 commit，再建立修复分支、生成基线报告。

**先修复已确认的 P0：敏感文件暴露、Python 锁文件、TypeScript 编译错误和 CI 失败；随后严格按阶段实施。**
