# 依赖包、重复引用与简体中文注释审计

> 审计基线：2026-11-08；目标是生产稳定性，不以“版本号最大”作为唯一升级标准。
> 版本来源优先使用项目官网、官方发行说明、PyPI / npm 官方 Registry 和 RustSec。

## 2. 已实际调整的依赖

### Python 后端

| 包 | 调整后的版本约束/锁定版本 | 处理理由 |
|---|---|---|
| FastAPI | `>=0.162.2,<0.163.0`；锁定 `0.162.2` | 官方 PyPI 已发布 0.162.2；更新 0.162.0 的旧锁定版本 |
| Pydantic | `>=2.14.3,<3.0`；锁定 `2.14.3` | 更新至官方 2026-11-05 稳定补丁版本 |
| pydantic-core | 锁定 `2.50.3` | 与 Pydantic 2.14.3 的精确核心依赖版本保持一致，不独立追到不兼容的 2.50.4 |
| ONNX Runtime | `>=1.31.1,<2.0`；锁定 `1.31.1` | 原锁定 1.20.1 已明显落后；官方 1.31.1 提供 Python 3.11 Linux x86_64 / ARM64 wheel，项目 CI 使用 Python 3.11 |
| NumPy | `>=2.4.4,<3.0`；锁定 `2.4.4` | 官方 NumPy 2.5.4 已要求 Python 3.12+；项目固定 Python 3.11，因此选择最新兼容稳定版 2.4.4，并在 CI 做 OpenCV / ONNX / InsightFace 导入冒烟验证 |
| Redis Python 客户端 | 暂保留 `5.3.1` 主版本线 | 不盲升 redis-py 8.x：官方兼容矩阵要求 Redis Server 7.2+；项目部署约定目前只写 Redis 7，不能假定所有生产实例均达到 7.2 |
| bcrypt / Passlib | 暂保留 bcrypt `4.0.1`、Passlib `1.7.4` | 现有密码哈希适配存在兼容约束；升级应先迁移/验证哈希后端，再升级，不能只改版本号 |

**移除/归类：**
- 从后端运行依赖中移除 `aiofiles`：对象存储和上传路径使用标准库 `asyncio.to_thread` / FastAPI `UploadFile`，未发现必须依赖 aiofiles 的业务用途；CI 新增依赖引用审计，若存在遗漏的静态引用会阻断。
- `aiosqlite` 是测试数据库驱动，不应随生产后端运行依赖安装；从后端运行锁文件移出，保留在测试依赖中。
- `httpx` 同时属于后端运行时 HTTP 客户端和测试客户端；在测试清单中保留精确版本，是为了测试环境可独立安装，不代表重复安装多个运行副本。
- `python-dotenv`、`python-multipart`、`aiomysql`、`pymysql`、`websockets`、`uvicorn`、`gunicorn` 等依赖可能由配置、SQLAlchemy 方言、FastAPI/Starlette、Uvicorn 或 CLI 动态加载；不能仅因业务源码没有直接 import 就误删。依赖审计脚本为这类依赖登记了明确用途。

### Node.js 与前端依赖

- Node.js 26 已进入 Active LTS；Node.js 24 仍在 Maintenance LTS。前端 engines 扩展为 Node 22.20+、24.12+、26+，CI 增加 Node 24 / 26 双版本构建矩阵。
- 当前 package-lock 已锁定 Axios 1.21.0、Vue 3.5.44、Element Plus 2.14.7、Vite 8.3.5 等版本。
- 官方 npm Registry 当前可见 Vue 3.5.45；Vite 官方发行页显示 8.3.6 为当前维护补丁。当前 lock 分别落后一补丁。
- **不手工伪造 package-lock 的 integrity / resolved / 子依赖树。** Vue 补丁升级会联动多个 `@vue/*` 包，Vite 也有 Rolldown 等传递依赖；必须用固定 npm 版本执行 npm lockfile regeneration，再跑 Node 24/26 双构建和 npm audit。当前 PR 已增加双版本 CI；完整 npm lockfile 刷新仍需单独验证，不宣称已经完成。
- Pinia 仍在 2.x、Vue Router 仍在 4.x、TypeScript 仍在 5.x。官方 registry 已出现更高主版本，但主版本升级存在 API / 类型 / 构建变化，暂不混入补丁升级；须单独做迁移 PR 和回归。

### Rust DLL

- `Cargo.lock` 当前包含 120 个 package 条目，直接依赖均通过 Cargo lock 固定解析。
- 新增 CI：Rust 1.74.0 与 stable 两条工具链执行 `cargo test --locked`；stable 额外执行 `cargo audit --deny warnings`。
- 若 1.74 的依赖 MSRV 验证失败，应根据实际失败的 crate 提高 `rust-version` 并同步 README，不能只保留一个不真实的最低版本声明。

## 3. 重复引用与未使用依赖检查

CI 新增以下自动检查：

1. `scripts/check_duplicate_imports.py`：扫描后端、迁移、脚本和测试 Python 文件，检测同一词法作用域内完全重复的 import 语句。
2. `frontend/scripts/check_duplicate_imports.mjs`：使用项目已有 TypeScript AST，扫描前端、小程序 JS/TS/Vue 脚本，检测同一文件重复 import / require。
3. `scripts/check_python_dependency_usage.py`：将后端直接依赖映射到 Python import 名称；框架动态加载、CLI 和数据库方言依赖必须登记用途，未登记依赖阻断 CI。
4. `frontend/scripts/check_dependency_usage.mjs`：检查前端直接依赖是否在源码、配置、测试或 npm scripts 中引用；仅对自动加载的类型声明包提供明确 allowlist。
5. 原有 `scripts/check_requirements_lock.py` 继续检查后端直接依赖是否存在精确锁定、版本约束和平台 marker 是否一致。
6. 原有 `pip-audit` / `npm audit` 继续执行；新增 RustSec Cargo audit。

注意：重复 import 检查是静态检查，不会把不同模块中合法的同名 import 当成重复；也不会自动删除代码。动态 `importlib`、插件入口点、字符串加载必须保留人工审查。

## 4. 锁文件当前边界与后续工作

`backend/requirements.lock` 目前是精选精确版本清单，不是完整的 transitive + hash lock；文件头已明确说明未列出的传递依赖仍由 pip 解析。当前 CI 的 `pip-audit` 可审计安装清单，但这不等于构建完全可复现。

后续建议单独建立依赖锁文件迁移：
- 采用 uv lock / uv sync 或 pip-tools `pip-compile --generate-hashes`；
- 分离 runtime、test、Windows-only、face/onnx 等可选依赖组；
- 按 Ubuntu 22.04 x86_64、ARM64、Windows x64 分别验证 wheel 可用性；
- 对人脸识别链路执行 buffalo_l 模型加载、embedding 维度、相似度、并发和内存回归；
- 所有锁文件通过 CI 后再合并。

## 6. 简体中文注释约定

关键业务逻辑优先使用简体中文注释，重点说明“为什么这样做、什么条件下不可改变”，避免只翻译代码表面含义。重点模块包括：
- 数据库事务边界、隔离级别、连接池；
- Redis 连接池、锁 owner token、缓存击穿/雪崩和降级边界；
- 库存条件 UPDATE、行锁顺序、门店库存覆盖规则；
- 支付回调验签、商户身份、幂等回执、退款查询和事务边界；
- Outbox 重试、租约、幂等和最终一致性；
- 人脸授权、特征提取、活体检测、加密和模型并发；
- 上传路径校验、MIME/魔数、SSRF 和对象存储。

新增/修改的关键注释统一使用简体中文；协议字段、第三方 API 名称、代码标识符和标准术语保持原文，避免误译。
