### 密码哈希渐进迁移

- 新创建或重置的员工密码统一生成 Argon2id 哈希。
- 历史数据库中的 bcrypt 哈希（包括原 Passlib 1.7.4 生成的格式）仍由 pwdlib 的 BcryptHasher 验证。
- 旧 bcrypt 用户登录或锁屏解锁成功后，`verify_and_update` 返回新的 Argon2id 哈希，并在当前请求事务内保存；错误密码不会修改哈希。
- bcrypt 保留 4.x 验证线（`<5.0`），避免 bcrypt 5 对超过 72 字节输入的行为变化影响历史密码；新哈希不再依赖 bcrypt。
- 新增回归测试覆盖 Argon2id 新哈希、旧 bcrypt 成功迁移、错误密码不迁移、损坏哈希 fail-closed。
- 不做批量离线重哈希，也不要求员工强制改密；升级随成功认证渐进完成。

**移除/归类：**
- 从后端运行依赖中移除 `aiofiles`：对象存储和上传路径使用标准库 `asyncio.to_thread` / FastAPI `UploadFile`，未发现必须依赖 aiofiles 的业务用途；CI 新增依赖引用审计，若存在遗漏的静态引用会阻断。
- `aiosqlite` 是测试数据库驱动，不应随生产后端运行依赖安装；从后端运行锁文件移出，保留在测试依赖中。
- `httpx` 同时属于后端运行时 HTTP 客户端和测试客户端；在测试清单中保留精确版本，是为了测试环境可独立安装，不代表重复安装多个运行副本。
- `python-dotenv`、`python-multipart`、`aiomysql`、`pymysql`、`websockets`、`uvicorn`、`gunicorn` 等依赖可能由配置、SQLAlchemy 方言、FastAPI/Starlette、Uvicorn 或 CLI 动态加载；不能仅因业务源码没有直接 import 就误删。依赖审计脚本为这类依赖登记了明确用途。

## 3. 重复引用与未使用依赖检查

CI 新增以下自动检查：

1. `scripts/check_duplicate_imports.py`：扫描后端、迁移、脚本和测试 Python 文件，检测同一词法作用域内完全重复的 import 语句。
2. `frontend/scripts/check_duplicate_imports.mjs`：使用项目已有 TypeScript AST，扫描整个 frontend 目录及双端小程序 JS/TS/Vue 脚本，检测同一文件重复 import / require。
3. `scripts/check_python_dependency_usage.py`：将后端直接依赖映射到 Python import 名称；框架动态加载、CLI 和数据库方言依赖必须登记用途，未登记依赖阻断 CI。
4. `frontend/scripts/check_dependency_usage.mjs`：检查前端直接依赖是否在源码、配置、测试或 npm scripts 中引用；仅对自动加载的类型声明包提供明确 allowlist。
5. 原有 `scripts/check_requirements_lock.py` 继续检查后端直接依赖是否存在精确锁定、版本约束和平台 marker 是否一致。
6. 原有 `pip-audit` / `npm audit` 继续执行；新增 `npm ls --all` 完整依赖树校验、RustSec Cargo audit 和 Rust 未使用依赖检查。

注意：重复 import 检查是静态检查，不会把不同模块中合法的同名 import 当成重复；也不会自动删除代码。动态 `importlib`、插件入口点、字符串加载必须保留人工审查。测试中有一项刻意验证过期异步属性触发 MissingGreenlet 的反例；该测试对 SQLAlchemy/aiosqlite 产生的 cursor 协程警告使用测试级精确过滤，正常菜单/营销序列化另有 `RuntimeWarning` 转错误的独立回归检查。

## 4. 锁文件完整性与剩余边界

- `backend/requirements.lock` 已从精选 pin 升级为完整 Linux 运行时版本锁：CI 在 Python 3.11.18 / Ubuntu 环境安装后用 `pip freeze` 生成，当前包含 98 个运行时分发包的精确版本。
- `scripts/check_requirements_lock.py` 不再只检查直接依赖；它会比对当前已安装的运行时 distribution，任何未写入 lock 的传递依赖都会阻断 CI。
- `dependency-lock-consistency` Job 每次 PR 都重新解析并校验锁文件；若锁文件漂移，会在受限的本 PR 分支自动提交生成结果。
- 当前 Python 锁固定版本但**尚未包含 wheel/sdist 哈希**，因此不应称为 hash-locked；后续可单独引入 pip-tools `pip-compile --generate-hashes` 或 uv universal lock。
- `frontend/package-lock.json` 已由 npm 11.19.1 在 CI 中刷新，Node 24 执行 `npm ci`、`npm audit` 和构建通过；Node 24/26 双版本构建均通过。CI 会校验 package.json 允许范围内的最新 lockfile 图。
- Rust Cargo.lock 继续使用 Cargo 原生校验；Cargo audit 和未使用依赖检查通过。

剩余平台边界：
- 当前 Python lock 目标是 Ubuntu 22.04 / Python 3.11 生产环境；Windows-only 的 pywin32 和 Python 3.13+ 的 audioop-lts 通过 marker 保留，但其他平台的完整依赖闭包仍应分别生成与验证。
- 人脸识别链路仍需在真实生产机上执行 buffalo_l 模型下载/加载、embedding 维度、相似度、并发和内存回归。

## 6. 简体中文注释约定

关键业务逻辑优先使用简体中文注释，重点说明“为什么这样做、什么条件下不可改变”，避免只翻译代码表面含义。重点模块包括：
- 数据库事务边界、隔离级别、连接池；
- Redis 连接池、锁 owner token、缓存击穿/雪崩和降级边界；
- 库存条件 UPDATE、行锁顺序、门店库存覆盖规则；
- 支付回调验签、商户身份、幂等回执、退款查询和事务边界；
- Outbox 重试、租约、幂等和最终一致性；
- 人脸授权、特征提取、活体检测、加密和模型并发；
- 上传路径校验、MIME/魔数、SSRF 和对象存储。

新增/修改的关键注释统一使用简体中文；协议字段、第三方 API 名称、代码标识符和标准术语保持原文，避免误译。
