# 一、最高优先级目标

本次修改最重要的目标：

## 1. 第一次扫码绝对不能强制用户注册会员

用户第一次来到面馆：

```text
扫描桌台二维码
↓
进入微信/支付宝小程序
↓
自动完成渠道身份识别
↓
后台创建或找到 Customer
↓
Customer 状态为 GUEST
↓
自动绑定当前门店和桌台会话
↓
直接进入菜单
↓
立即点餐
```

不得强制：

- 填昵称
- 上传头像
- 填手机号
- 点击注册
- 完善会员资料
- 关注公众号
- 领取会员卡

才能点餐。

---

# 二、彻底区分“用户身份”和“会员注册”

当前项目必须明确区分：

## A. 用户身份 Identity

微信/支付宝授权以后：

```text
用户可以被识别
```

但这不代表：

```text
用户已经主动注册会员
```

---

## B. 游客身份 GUEST

第一次微信/支付宝授权后：

```text
自动创建 Customer
```

这是允许的。

但是：

```text
member_status = GUEST
```

而不是 MEMBER。

---

## C. 会员 MEMBER

只有用户明确主动点击：

```text
开启智能会员
```

或者明确同意：

```text
加入会员
```

以后，才：

```text
GUEST → MEMBER
```

---

# 三、不要再使用 profile_completed 作为“是否已经注册”的唯一判断

当前项目如果存在：

```text
profile_completed
```

不要让它同时承担：

- 是否存在用户
- 是否登录
- 是否完成会员注册
- 是否填写昵称
- 是否绑定手机号

等多个含义。

必须拆分。

至少建立：

```text
account_status
member_status
profile_status
phone_verified
```

建议：

```text
account_status:
ACTIVE
DISABLED
DELETED

member_status:
GUEST
MEMBER

profile_status:
EMPTY
PARTIAL
COMPLETED
```

如果项目已有类似字段，优先兼容现有数据库，不要无意义重复字段。

# 四、微信用户识别逻辑

完整审查并修复微信登录。

正确逻辑：

```text
wx.login()
↓
获得 code
↓
发送后端
↓
后端向微信服务端换取用户身份
↓
获得稳定渠道身份
↓
查询 customer_wechat_accounts
↓
存在：
    找到 customer_id
不存在：
    创建 Customer
    创建 CustomerWechatAccount
    member_status = GUEST
↓
返回业务 session/token
```

注意：

不要把：

```text
wx.login() 返回的 code
```

直接当成永久用户 ID。

必须使用服务端验证后获得的稳定微信身份标识。

# 五十、最终产品原则

请牢记：

> **用户第一次扫码的目的不是注册会员，而是吃饭。**

系统应该：

```text
微信/支付宝授权
        ↓
自动识别用户
        ↓
自动创建游客身份
        ↓
直接点餐
        ↓
自动学习口味
        ↓
在合适的时机引导会员
```

而不是：

```text
扫码
 ↓
注册会员
 ↓
填写资料
 ↓
才能点餐
```

最终目标是做到：

> **“无感登录、无感建档、无感点餐、主动会员化、持续学习口味。”**

完成所有修改后，再对整个项目做一次从：

```text
扫码 → 登录 → 用户识别 → 桌台 → 菜单 → 购物车 → 订单 → 支付 → 回调 → 厨房 → 完成 → 会员 → 口味学习
```

的完整端到端审计，确保不存在前后端逻辑不一致、状态机断裂、重复订单、重复支付、重复会员、跨桌台、跨用户、跨门店等问题。
