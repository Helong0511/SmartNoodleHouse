# 退款说明

退款分两条路径：持有 `payment:refund` 的管理端直连退款，以及收银员提交、店长审批的 POS 退款申请。

## 支付退款（管理端）

1. 校验订单 / 支付单可退余额。
2. 写入 `payment_refunds`（含 `idempotency_key`），调用微信 / 支付宝退款 API。
3. 异步结果：退款回调或调度轮询（`retry_count` / `next_retry_at` / `last_error`）。
4. 成功后回写订单支付状态、积分扣回、券回滚（按业务规则）、`financial_ledger` 记 REFUND。

## POS 退款申请

- 收银员对本班订单创建 `pos_refund_requests`（`PENDING`）。
- 店长 / 超管审批：通过则走真实退款；拒绝 / 取消更新状态。
- 组合支付按 tender 分摊；`executed_amount` 记录已成功金额。

## 安全注意

- 生产关闭 `ALLOW_PAYMENT_MOCK`。
- 退款回调与支付回调同样验签；可配置 `WECHAT_REFUND_NOTIFY_URL`（空则复用支付通知 URL）。
- 敏感操作写入 `operation_logs`。

## 相关配置（名称级）

- `WECHAT_REFUND_NOTIFY_URL` / `WECHAT_API_V3_KEY` / 平台证书
- `ALIPAY_*` 退款与验签公钥
- 权限码：`payment:refund`

详见 [payment.md](payment.md)。

## 退款一致性与异常分支补充（2026-11-08）

退款不得把“请求已发送”当成“退款成功”。生产处理必须区分 REQUESTED / PROCESSING / SUCCESS / FAILED / UNKNOWN 等真实渠道状态，并保留可重试与对账路径。

审查重点：
- 渠道退款成功响应必须完整匹配退款单号、原支付交易号、订单号、商户/应用身份和退款金额；缺字段或不匹配时不得升级为 SUCCESS。
- 查询渠道退款状态失败、网络超时、响应无法解析时，保留待确认状态，不能把本地订单直接标记已退款或已关闭。
- 退款幂等键应基于稳定业务身份，不应依赖可变通知时间字段。
- 本地财务分录、积分扣回、券回滚等副作用要在同一事务或可靠 Outbox 中保证幂等；台账失败不能被静默吞掉。
- POS 部分退款、组合支付、重复点击、并发审批必须以 DB 锁/唯一约束保护累计可退金额。
- 对账差异必须有可追踪批次、人工处理状态和审计记录。

测试必须覆盖渠道已退款但本地未提交、回调重复/乱序、金额不匹配、身份字段缺失、Redis 不可用、数据库事务回滚和进程中断。审查证据见 [FULL_CODE_REVIEW_2026-11-08.md](audit/FULL_CODE_REVIEW_2026-11-08.md)。
