# 多门店

## 数据隔离模型

- `stores`：门店主数据（`store_no` 参与业务单号前缀）。
- 员工 `users.store_id`：非空则仅能操作该店；`NULL` 表示超管可跨店。
- 业务表普遍带 `store_id`（订单、支付班次、库存、摄像头、外卖映射等）。
- 桌台 `tables` 在店内唯一 `(store_id, table_no)`；扫码令牌 `qr_token` 全局唯一。

## 角色与门店

| 角色 | 典型 store_id | 能力摘要 |
|------|---------------|----------|
| SUPER_ADMIN | NULL | 全店；系统配置 |
| STORE_ADMIN | 本店 ID | 本店运营与退款 |
| CASHIER / KITCHEN / OPERATOR | 本店 ID | 按权限矩阵收敛 |

生产基础数据见 `sql/struct.sql` + `sql/data_sys.sql` + `sql/data_custom.sql`；Python 种子脚本用于幂等维护。

## 运营注意

- 新增门店：插入 `stores`，再配桌台、库存、外卖 `platform_store_bindings`、员工绑定。
- 顾客 `registered_store_id` / `registered_table_id` 仅记录首次扫码注册门店 / 桌台。
- 统计与财务分录（`financial_ledger.store_id`）按店过滤；跨店报表仅超管。
- 顾客合并：`POST /api/customers/{target_id}/merge`（需 `customer:write`）。非超管要求源/目标顾客均在本店下过单；合并策略见 `CustomerMergeService` docstring。
- 优惠券模板：`coupon_templates.store_id` 为 NULL 表示总部模板（各店可见可发）；非空仅该店可管/可发。发券与持券列表对门店账号按本店顾客隔离。
- 小程序 / H5 通过桌台或门店上下文解析 `store_id`，服务端必须以落库关联为准，勿信任客户端随意传店。

## 双层配置三条铁律（总部 ∪ 门店）

库表允许 `store_id NULL`（总部）与门店行同业务键并存，这是**门店覆盖**能力，不是数据错误。按消费场景处理：

1. **类型 A 可选档位/选项卡**（储值档、积分兑券）：后台列表展示「总部 ∪ 本店」并标范围；顾客端/小程序**必须按业务键合并，门店覆盖总部**，禁止出现两张同档卡。
2. **类型 B 运行时解析规则**（系统参数、社福规则、欢迎券同名、外卖分类映射、营销同 `code` 推荐加权/总部发券任务）：后台可看两者；结算/同步/加权**只取门店行，否则总部**。
3. **类型 C 可绑定资源 / 并行对象**（规格组、客户分群、营销活动本身）：后台不去重；对象 ID 不同可同时存在。营销活动另见下表「同 code 运行时」按类型 B。

### 冲突处理矩阵（怎么办）

| 对象 | 是否 HQ∪店双层 | 业务键 | 冲突怎么办 |
|---|---|---|---|
| 储值档 `recharge_packages` | 是 · A | `pay_amount` | 顾客端合并门店覆盖；门店保存同实付提示 `override_warning` |
| 积分兑券 `point_exchange_options` | 是 · A | `(template_id, points_cost)` | 同上；整表替换接口返回 `override_warning(s)` |
| 优惠券模板 `coupon_templates` | 是 · B（同名） | `name`（欢迎/同名解析） | 发券/欢迎按本店同名优先；门店建同名总部启用模板时提示；持券实例仍按模板 ID |
| 系统设置 / 门店设置 | 是 · B | `setting_key` | `SystemSettingsService` 门店覆盖平台 |
| 社福规则 `social_benefit_rules` | 是 · B | `identity_code` | 结算选规则门店优先于总部 |
| 外卖分类映射 `platform_category_maps` | 是 · B | `(platform, local_category_id)` | 同步解析 `resolve_category_maps` 门店覆盖；门店保存同键提示 `override_warning` |
| 外卖餐品映射 `delivery_product_maps` | **否** | 每店独立（`store_id` NOT NULL） | 无 HQ 默认行；按店维护平台 SKU |
| 营销活动 `marketing_campaigns` | 后台 C + 运行时 B | `code` | 列表不去重；创建/发布同 code 提示；推荐加权与总部 ISSUE 任务对本店让位门店活动 |
| 客户分群 `customer_segments` | 是 · C | `code`（店内唯一） | 不去重；门店可引用总部分群按本店圈人；门店建同编码总部预置时提示并行不覆盖 |
| 规格组 `option_groups` | 是 · C | `(store_scope, code)` | 编码前缀不同（总部 `0000-` / 门店编号）；同名仅提示，不自动覆盖 |
| **餐品 / 分类** `products` / `product_categories` | **否** | 每店独立 `store_id` | 无「总部餐品覆盖」；跨店用菜单复制；库存用 `store_product_stocks` |
| 会员等级 `member_levels` | 否（平台字典） | — | 全平台一套，无门店覆盖 |

业务键约定：储值=`pay_amount`；积分兑券=`(template_id, points_cost)`；社福=`identity_code`；设置=`setting_key`；外卖分类映射=`(platform, local_category_id)`；营销运行时=`campaign.code`；欢迎券=`template.name`。  
门店新建覆盖档时系统会提示「将覆盖…总部同…」；勿删范围唯一约束（那是覆盖能力的根基）。后台管理列表**禁止**调用 `merge_store_over_hq`（仅顾客选档与运行时解析调用）。

## 配置

门店级参数放 `store_settings`；全局参数放 `system_settings` 或环境变量。生产多实例共享同一库时，用 `PROCESS_ROLE=auto|leader|worker` + Redis Leader 锁保证调度不重复（而不是按店拆进程；当前版本按单库多店设计）。

## 多门店隔离审计补充（2026-11-08）

门店隔离不是只在列表 SQL 增加 store_id。以下全部必须绑定同一授权上下文：对象详情、创建/更新/删除、导入导出、支付与退款、WebSocket 频道、叫号屏令牌、上传文件、缓存 key、幂等 key、后台任务、外卖映射、报表与日志。

审查特别提示：
- 没有桌台 token 的 H5/外带订单也必须校验门店存在、营业状态、顾客与门店上下文；不能把客户端 store_id 当授权。
- display token 必须绑定 store_id，空 token 在任何敏感环境均拒绝，比较采用恒定时间函数。
- WebSocket 顾客连接必须有可验证的 customer/order/store 投递上下文，不能“握手成功但没有消息”。
- 幂等键不能简单截断长 scope 后丢失 digest；应使用长度受控的 scope 编码与完整摘要。
- HQ 与门店覆盖规则需按业务类型定义唯一业务键、优先级和冲突处理；总部配置与门店配置不能随意合并或误覆盖。

回归测试必须使用至少两个门店和两种角色，验证跨店读、写、删除、退款、WebSocket、文件、缓存、幂等与后台任务。逐条发现见 [全量审查报告](audit/FULL_CODE_REVIEW_2026-11-08.md) 与 [门店隔离检查清单](门店隔离检查清单.md)。
