# 支付说明

## 渠道

| Provider | 场景 | 备注 |
|----------|------|------|
| WECHAT | 小程序 / 相关扫码 | 商户号、APIv3、平台证书验签 |
| ALIPAY | 小程序 JSAPI 等 | 应用私钥 / 支付宝公钥；手机号解密需 AES Key |
| CASH | POS 现金 | 无第三方回调 |
| MOCK | 仅开发 | `ALLOW_PAYMENT_MOCK=true`；生产禁止 |

## Mock 开关一览（仅开发，生产启动校验强制关闭）

| 开关 | 作用 |
|------|------|
| `ALLOW_PAYMENT_MOCK` | 支付渠道 MOCK：不调真实收银台，直接落支付成功 |
| `ALLOW_AUTH_MOCK` | 登录 Mock：`mock:` 前缀 auth code 可登录（免真实平台网关） |
| 手机号调试链路 | 仅 `APP_ENV=development`：`mock:debug` 凭据 / 手输手机号（保存为未验证，不合并账号）；生产返回 40054 |

> 调试手机号链路不触碰支付：绑定成功后走正常下单支付流程，便于端到端联调出餐提醒。
> 回调与对账不受 Mock 影响：真实渠道支付必须走 notify 验签，Mock 单据无回调。

## 主流程

1. 创建支付单 `payments`（关联 `orders`，POS 写入 `operator_id`）。
2. 调起渠道下单，拿到客户端调起参数。
3. 异步通知进入回调接口 → 验签 → 幂等（Redis + `payment_callback_receipts`）→ 更新支付 / 订单状态 → 积分与券核销等。
4. 退款写入 `payment_refunds`；可配置退款回调或主动查询轮询（含 `retry_count` / `next_retry_at` / `last_error` / `idempotency_key`）。

## 收银与权限

- 收银员通常无 `payment:refund`：对本班订单提交 `pos_refund_requests`，由店长 / 超管审批执行。
- 店长 / 超管持有 `payment:refund`，可管理端直连退款。
- 班次表 `cashier_shifts` 用于开班备用金与交班汇总。

## 财务账本

`financial_ledger` 记录 SALE / REFUND / ADJUSTMENT 分录，便于按门店对账；与 `payments` 流水互补，不替代渠道对账单。

支付成功（含分笔）与退款成功、外卖落单/退款会写入账本；Dashboard 净收入在有分录时优先从账本汇总（允许为负）。

## 回调与安全

- 通知 URL 必须公网 HTTPS，与商户平台配置一致。
- 生产关闭一切 Mock；配置 `WEBHOOK_IP_ALLOWLIST`（如适用）与 `TRUSTED_PROXY_IPS`。
- 密钥轮换见 [security.md](security.md)；文档与示例仅使用虚假占位符。

## 相关配置（名称级，无真实值）

- `WECHAT_MCH_ID` / `WECHAT_API_V3_KEY` / `WECHAT_NOTIFY_URL` / `WECHAT_REFUND_NOTIFY_URL`
- `ALIPAY_APP_ID` / `ALIPAY_PRIVATE_KEY` / `ALIPAY_PUBLIC_KEY` / `ALIPAY_NOTIFY_URL` / `ALIPAY_AES_KEY`
- `ALLOW_PAYMENT_MOCK`

## 资金安全审计补充（2026-11-08）

以下为审查报告发现的风险点，必须在代码层逐项修复并验证后才能关闭：

- 支付金额必须从渠道响应的真实字段解析，并与本地支付单金额、币种、商户号、应用号、订单号逐项匹配；缺失金额字段必须拒绝入账，不能走“未取到金额就继续结算”分支。
- 付款码支付、充值支付、组合支付、分笔支付都要验证金额；不能只验证普通小程序支付。
- 回调幂等键优先使用平台不可变事件 ID；不要把可变 success_time 等时间字段当作身份组成部分。事件 ID 必须从原始通知透传到 verifier 解析结果。
- 财务 SALE/REFUND 分录失败不能只记录日志继续确认支付；必须同事务写入或可靠 Outbox，失败时 fail-closed。
- 抹零、折扣和部分支付必须同步更新订单应收总额、已付金额、未付余额和财务科目，避免永远停留 PARTIAL_PAID。
- 查单或关单请求异常/超时不能推断渠道未支付；保持 PENDING/UNKNOWN 并重试、对账。
- 充值幂等键命中必须校验 customer、store、package、pay_amount、gift 等所有业务参数，不一致返回冲突。
- 秒杀免费单也必须统一支付状态、Payment/财务记录、订单状态机和支付后副作用。
- 退款成功必须严格匹配退款单号、原交易号、订单号和金额；缺失身份字段不应按金额单独放行。
- 充值结算必须能抵御进程在支付状态和充值状态写入之间崩溃后的重复执行。

测试至少覆盖金额篡改、字段缺失、重复/乱序通知、相同幂等键不同 payload、支付成功但查单超时、台账写入失败、退款并发、进程崩溃恢复。详细条目见 [全量代码审查报告](audit/FULL_CODE_REVIEW_2026-11-08.md)。
