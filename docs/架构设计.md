# 系统架构与信任边界

> 当前说明基于 main @ 442beb4761b29f5b415830e91e06c97241f74ef3；部署/代码行为以实际配置、CI 和当前源代码为准。审查发现的问题状态见 docs/audit/FULL_CODE_REVIEW_2026-11-08.md。

SmartNoodleHouse 是多门店面馆经营系统，包含后台、微信/支付宝小程序、H5 扫码、POS、厨房 KDS、顾客叫号屏、人脸迎宾、会员营销及美团/饿了么外卖接入。

## 1. 逻辑分层

| 层 | 目录 | 职责 |
|---|---|---|
| 顾客端 | miniprogram-wechat、miniprogram-alipay、H5 | 扫码、菜单、购物车、下单、支付、会员、订单跟踪 |
| 管理端 | frontend | 总部/门店运营、商品、订单、支付退款、库存、会员、摄像头 |
| API | backend/app | 身份、授权、业务规则、交易编排、Webhook、实时推送 |
| 持久化 | MySQL + Alembic | 订单、支付、财务、库存、门店、会员、审计 |
| 协调与缓存 | Redis | 限流、幂等辅助、Leader 锁、Pub/Sub、活体挑战及缓存 |
| 异步任务 | Outbox/Inbox + Leader worker | 支付副作用、Webhook 消费、重试、定时任务、打印 |
| 边缘设备 | camera / Nginx 内网访问 | 摄像头 RTSP、识别、TTS |

## 2. 部署拓扑

```
微信/支付宝小程序、H5、管理端、平台回调
             │ HTTPS 443
             ▼
           Nginx
             │ 127.0.0.1:8000
             ▼
     Uvicorn 原生多 worker
       ├── FastAPI API
       ├── MySQL（业务真源）
       ├── Redis（协调/缓存）
       └── Leader 锁选出的单实例任务
             ├── APScheduler
             ├── Outbox / Inbox worker
             ├── TTS
             └── 摄像头采集/识别
```

生产服务由 systemd 管理，后端 Uvicorn 原生多 worker，不依赖 Gunicorn worker 插件。所有 worker 通过 Redis Leader 锁及 DB fencing/唯一约束协调；不得假设“一个进程只会启动一次”。MySQL、Redis 不对公网开放。摄像头 RTSP 仅允许店内可信网络访问。

## 3. 核心业务闭环

1. 堂食：桌台二维码 → 服务端解析桌台/门店上下文 → 服务端重算价格和优惠 → 创建幂等订单 → 微信/支付宝支付 → 回调验签及对账 → KDS → 出餐/完成。
2. POS：员工认证与门店权限 → 班次 → 收银/扫码 → 订单及财务流水 → 退款审批/交班。
3. 外卖：平台回调验签 → Inbox 持久化 → 异步消费 → 统一订单与门店映射 → KDS → 平台状态回传。
4. 会员：明确授权后绑定资料/手机号/人脸；支付后积分和券副作用通过事务及 Outbox 处理；退款按规则回滚。
5. 多门店：总部配置与门店覆盖按业务类型区分；每个读写、缓存、任务、WebSocket、文件和统计都必须执行门店范围校验。
6. 营销/秒杀：总部定义活动、门店参与范围、资格与库存；数据库原子扣减和唯一约束是最终并发保障，Redis 锁只是协调手段。

## 4. 信任边界

- 浏览器/小程序传入的金额、单价、折扣、store_id、活动规则、订单状态和完成标记均不可信。
- 员工、顾客、服务账号和叫号屏使用不同身份/凭证；令牌必须绑定主体、用途、门店和有效期。
- 平台回调不因来源 IP 或 HTTP 200 而可信，必须验签、核对商户/应用/订单/金额/币种并做幂等。
- Redis 不作为财务数据真源；数据库约束、事务、行锁和审计记录负责最终一致性。
- 日志和错误响应属于数据外发边界，任何 SDK/HTTP 客户端的请求 URL、query 和 headers 都要脱敏。
