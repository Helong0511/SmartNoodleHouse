# 人脸迎宾、称呼与智能推荐说明

本文说明：顾客「怎么称呼」、迎宾语如何用占位符配置、口味/餐品智能推荐从哪来、如何出现在迎宾播报与小程序里。

相关技术文档：[人脸识别说明](./人脸识别.md)（授权、匹配阈值、加密、Worker）。

---

## 1. 总览

| 能力 | 数据从哪来 | 用在哪里 |
|------|------------|----------|
| **称呼** | 顾客展示名 / 昵称 / 会员等级 | 迎宾 TTS、迎宾日志、后台展示 |
| **迎宾语** | 门店可配模板 + 占位符替换 | 人脸识别成功后的播报文案 |
| **口味偏好** | 历史已付订单的规格选项 | 迎宾 `{口味}`、顾客详情、小程序智能口味条 |
| **餐品推荐** | 行为画像 + 协同过滤 + 热销/场景 | 迎宾 `{餐品}`、小程序「猜你喜欢」等 |

人脸迎宾触发条件（简述）：顾客已主动授权人脸 → 摄像头匹配达标 → 多帧确认 → 冷却期内未重复迎宾 → 拼文案 → TTS + 写 `welcome_logs` + WebSocket 推送「迎宾日志」。

## 2. 顾客管理里的「展示名」和「昵称」

路径：**会员 → 顾客管理 → 详情**。

| 字段 | 库表字段 | 建议用途 |
|------|----------|----------|
| **展示名** | `customers.display_name` | 店员口头怎么叫（如「老张」）；迎宾 `{称呼}` **优先** |
| **昵称** | `customers.nickname` | 小程序侧常用名；展示名为空时作 `{称呼}` |

### 2.1 `{称呼}` 取值规则

1. 有效 **展示名**（非空，且不是占位词）  
2. 否则有效 **昵称**  
3. 否则为空字符串（由模板决定怎么说）

**占位词**（不算有效称呼，会跳过）：`微信用户`、`支付宝用户`、`面馆会员`、`联调员` 等。

后台改展示名/昵称时，会尽量同步到微信/支付宝渠道账号昵称，避免小程序仍显示旧名。

### 2.2 `{会员等级}` 取值

来自 `member_levels.name`（如「银卡会员」「金卡会员」），按顾客当前 `member_level_id`。

无等级时该占位符为空。

### 2.3 无展示名/昵称时的兜底

- 主模板里 **写了** `{会员等级}`：`{称呼}` 可为空，例如变成「尊贵的 金卡会员…」（多余空格会压缩）。  
- 主模板里 **没写** `{会员等级}`：系统会把 `{称呼}` 兜成 `尊贵的{等级名}`（如「尊贵的金卡会员」），避免只剩「欢迎回来，。」。

## 3. 迎宾语模板与占位符（按店配置）

路径：**系统设置 → 迎宾与人脸**（选门店可覆盖）。

| 配置项 | setting_key | 作用 |
|--------|-------------|------|
| **迎宾语模板** | `welcome_greeting_prefix` | 主句 |
| **口味偏好附句** | `welcome_preference_template` | 有口味且主句未写 `{口味}` 时追加 |
| **餐品推荐附句** | `welcome_product_template` | 有推荐餐品且主句未写 `{餐品}` 时追加（默认空=不追加） |

种子默认主句：`欢迎回来，{称呼}。`  
默认口味附句：`今天还是老样子：{口味}？`  
默认餐品附句：空（需要播餐品时请在主模板写 `{餐品}`，或配置附句如 `要不要来份{餐品}？`）。

### 3.1 支持的占位符

| 中文 | 英文别名 | 含义 |
|------|----------|------|
| `{称呼}` | `{name}` | 展示名 → 昵称 →（见上兜底） |
| `{会员等级}` | `{level}` | 当前会员等级名称 |
| `{店名}` | `{store}` | 触发摄像头所属门店的 `stores.name` |
| `{口味}` | `{taste}` | 口味偏好 Top2，用顿号连接 |
| `{餐品}` | `{product}` | 智能推荐餐品 Top2 菜名，用顿号连接 |

未识别的 `{xxx}` 不会替换，请勿自造占位符。

### 3.2 配置示例（你要的效果）

**迎宾语模板**填：

```text
尊贵的 {称呼} {会员等级}，欢迎您再次光临{店名}
```

| 占位符 | 值 | 结果片段 |
|--------|-----|----------|
| 称呼 | 老张 | 老张 |
| 会员等级 | 金卡会员 | 金卡会员 |
| 店名 | 肠旺面（总店） | 肠旺面（总店） |

播报：

```text
尊贵的 老张 金卡会员，欢迎您再次光临肠旺面（总店）
```

若还有口味偏好（主模板未写 `{口味}`），会再追加默认附句，例如：

```text
尊贵的 老张 金卡会员，欢迎您再次光临肠旺面（总店）。今天还是老样子：辣度·微辣、宽细·细面？
```

把口味/餐品写进主句的例子：

```text
尊贵的 {称呼}，欢迎来到{店名}。今天还是 {口味}，要不要来份{餐品}？
```

### 3.3 兼容旧写法

若配置里 **没有任何** `{…}` 占位符（例如只写「欢迎回来」），按旧逻辑拼成：

```text
欢迎回来，{称呼或尊贵的等级}。
```

再按规则追加口味/餐品附句。

### 3.4 其它迎宾相关参数

| 参数 | 说明 |
|------|------|
| `welcome_cooldown_seconds` | 同一顾客两次迎宾最小间隔 |
| `face_match_threshold` | 人脸相似度阈值 |
| `face_confirm_frames` | 连续匹配帧数 |
| `enable_face_welcome` | 会员中心是否显示人脸迎宾开关（平台级） |

实现代码：`backend/app/services/face_service.py` → `WelcomeService.try_welcome` / `build_welcome_text`。  
记录表：`welcome_logs.welcome_text`。后台 **迎宾 → 迎宾日志** 可查历史播报。

## 4. 口味智能推荐（规格偏好）

### 4.1 数据怎么来的

1. 顾客下单并 **支付成功**（或相关支付侧效应）后，触发 `PreferenceService.recompute_for_customer`。  
2. 取该顾客近期最多 **40** 笔已付订单（`PAID` / `PARTIAL_REFUND`；全额退款不参与）。  
3. 按订单明细的 **规格选项**（`order_item_options`：分组名 + option_code / 名称）聚合。  
4. 写入 / 更新表 `customer_preferences`：类别、选项码、选项名、次数、偏好分、最近使用时间。

加权要点：

- 份数加权（买 2 份算更重）  
- **越新的订单权重越高**（衰减系数，口味变化会慢慢改掉旧偏好）  
- 午/晚高峰、周末略加权  
- 部分退款订单降权  

### 4.2 迎宾怎么用

迎宾取 `PreferenceService.get_recommendations` 返回列表的 **前 2 条**，拼成 `{口味}`，例如：`辣度·微辣、宽细·细面`。

筛选逻辑简述：

- 优先 `order_count ≥ 2` 的偏好；没有则退回全部（首单也能出）  
- 再优先高分偏好；可叠加季节/天气等场景加权（`preference_scene_enabled`）

### 4.2.1 天气口味加权（读侧）

| 配置 | 含义 |
|------|------|
| `preference_scene_enabled` | **总开关**：季节 + 同星期同餐段 + 天气乘子 |
| `weather_pref_enabled` | **天气子开关**：需门店 `latitude`/`longitude`；关则仅季节等仍可生效 |
| 门店经纬度 | Open-Meteo 查实时气温与 WMO 天气码；失败静默降级（Redis 空值短缓存） |

天气粗分（`weather_client.condition_from_wmo`）：

| condition | 条件 | 规格偏好抬升方向（示例） |
|-----------|------|--------------------------|
| `hot` | 气温 ≥ 28℃（非雨） | 不辣/微辣/小碗/清汤/冰品 |
| `cold` | 气温 ≤ 10℃（非雨） | 加辣/特辣/大碗/浓汤 |
| `rainy` | WMO 降水/雷暴码 | 加辣/浓汤/大碗 |
| `mild` | 其余 | 天气不对规格额外加权 |

餐品推荐另按温度维/辣度维/汤类标签做 ±8% 内乘子（同 condition），理由文案如「天气炎热更清爽」。

运维：门店信息页「探测天气口味」→ `GET /api/settings/stores/{id}/weather-scene`。

### 4.3 后台 / 小程序哪里能看到

- **顾客详情**：智能记录的口味爱好、场景条（季节·天气℃）、`welcome_hint` 预览文案  
- **门店信息**：经纬度 + 探测天气；业务参数「系统通用」开关  
- **小程序**：点餐页「智能口味」；猜你喜欢副标题可带 `meta.scene.label`（如「夏季 · 炎热 32℃」）  
- 顾客可在隐私相关入口查看/清空口味画像（`/customers/me/taste-profile`）

## 5. 餐品智能推荐

与「口味」（规格）是另一条链路：推荐的是 **菜品本身**。

### 5.1 引擎做什么

服务：`RecommendationService.recommend`（`backend/app/services/recommendation_service.py`）。

小程序接口：`GET /api/miniprogram/recommendations?store_id=&scene=`  
场景：`recommend_menu`（点餐猜你喜欢）、`settle_addon`（结算加购）等。

按顾客状态分三档：

| 状态 | 含义 | 大致策略 |
|------|------|----------|
| **COLD** | 未登录 / 关闭个性化 / 无行为 | 热销 + 新品 / 店长推荐 |
| **WARM** | 有少量行为 | 内容相似 + 热销等混合 |
| **HOT** | 行为较多 | 个人画像 + 协同过滤（常点关联）+ 场景/活动加权 |

还会考虑：近期已购去重、分类推荐配置、季节天气、营销活动 boost、生日可见餐品等。理由文案例：「您常点的」「点过的人也常点」「店长推荐」。

### 5.2 迎宾怎么用 `{餐品}`

当主模板含 `{餐品}`，或配置了非空的「餐品推荐附句」时：

1. 用摄像头所属门店 `store_id`  
2. 调用推荐引擎 `scene=recommend_menu`，`limit=2`  
3. 取菜名填入 `{餐品}`（顿号连接）

示例主模板：

```text
{称呼}您好，欢迎光临{店名}。今天推荐您试试{餐品}。
```

示例附句（主模板不写 `{餐品}` 时）：

```text
要不要来份{餐品}？
```

**注意**：餐品附句默认留空，是为了避免播报过长；需要时再开。

### 5.3 与口味的区别（易混点）

| | 口味 `{口味}` | 餐品 `{餐品}` |
|--|---------------|---------------|
| 粒度 | 规格选项（微辣、细面…） | 菜品名称（肠旺面、冒菜…） |
| 表 / 服务 | `customer_preferences` / PreferenceService | 行为画像 + RecommendationService |
| 典型句 | 「今天还是老样子：辣度·微辣」 | 「要不要来份红烧牛肉面」 |

## 6. 端到端流程（人脸到店）

```text
摄像头抓帧
  → 人脸匹配（阈值 + 多帧）
  → 冷却抢占成功
  → 解析称呼 / 等级 / 店名
  → 按需拉取口味 Top2、餐品 Top2
  → 渲染迎宾语模板（+ 附句）
  → TTS 播报 + welcome_logs + 后台 WebSocket
```

小程序侧「猜你喜欢 / 智能口味」**不依赖**人脸；同一套偏好与推荐数据也可在点餐页使用。

---

## 7. 运营配置建议

1. **各店主模板**：统一品牌话术，用 `{称呼}` `{会员等级}` `{店名}`。  
2. **口味**：保留默认附句即可；也可把 `{口味}` 写进主句。  
3. **餐品**：播报短则主句加 `{餐品}`；想单独控制语气再配「餐品推荐附句」。  
4. **展示名**：收银/客服尽量维护真实称呼，迎宾更自然。  
5. 播报宜短：主句 + 至多一句口味/一句餐品，避免 TTS 过长。

## 9. 常见问题

**Q：改了模板为什么还是旧话？**  
A：确认改的是 **当前摄像头所属门店** 的覆盖值；平台默认与门店覆盖是两层。

**Q：有等级为什么没念出来？**  
A：主模板里必须写 `{会员等级}`；只写 `{称呼}` 且有展示名时，不会自动带等级。

**Q：有口味为什么没播？**  
A：顾客尚无足够已付规格数据；或主模板写了 `{口味}` 但偏好为空（空占位会被清理）。看顾客详情「口味爱好」。

**Q：餐品推荐为什么是热销不是常点？**  
A：新客 / 关闭个性化 / 行为少时走 COLD；多下几单且未关闭推荐后会更偏个人化。

**Q：小程序名和迎宾名不一致？**  
A：小程序优先渠道昵称；后台改展示名后应已同步渠道。仍不一致时检查渠道账号资料是否被端上再次覆盖。
