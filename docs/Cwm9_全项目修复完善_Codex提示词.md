# 四、P0：配置、秘密管理与生产启动安全

## 4.1 数据库默认凭证

重点核查实际配置（旧审计曾提及 `backend/app/core/config.py` 中数据库 URL 默认使用 root/password，但必须重新核实）。

实施要求：

1. 生产环境禁止默认 root 账户和弱口令连接。
2. 生产配置缺少数据库连接、签名密钥、加密密钥、支付必要配置时，启动校验必须失败并给出不泄密的错误提示。
3. 开发环境可以使用明确标注的本地示例配置，但示例密码不得被生产环境自动采用。
4. 提供 `.env.example`，仅包含变量名和无效占位符；确认 `.env`、私钥、证书和本地凭证被 Git 忽略。
5. 检查启动日志、异常堆栈和诊断端点，不得输出连接串或秘密。
6. 提供最小权限数据库账户权限清单和安全配置说明。

## 4.2 叫号屏、WebSocket 和内部端点

核查叫号屏令牌默认空值、可选认证、HTTP/WebSocket 鉴权和门店隔离。

- 生产模式不得允许无认证访问受保护的叫号屏数据。
- HTTP 和 WebSocket 必须使用一致的认证与授权规则。
- 令牌不得通过容易进入访问日志的 URL 查询参数传递；优先使用安全 Header、短期签名或项目支持的安全握手。
- 令牌应有足够熵、可轮换、可撤销，日志中应脱敏。
- 每次订阅、查询、重连都必须验证用户对目标门店的权限。
- 对连接数、消息大小、订阅频率和异常重连做限制。
- 为无权限、令牌过期、跨门店访问和断线重连增加测试。

## 4.3 Webhook 与第三方回调安全

逐个列出所有支付、外卖、打印、通知和其他 Webhook 路由，并为每个路由标明认证方式。

- 不得只依赖来源 IP。
- 对支持签名的平台，严格按官方协议验证原始请求体、签名、时间戳、随机数/事件 ID及必要的商户/应用身份。
- 先验证签名，再信任请求内容；防止 JSON 重新序列化造成验签偏差。
- 对时间窗口内的重放，使用持久化事件 ID/交易 ID唯一约束和幂等业务处理。
- IP 白名单只能作为纵深防御；正确处理可信反向代理，禁止无条件信任客户端传入的 `X-Forwarded-For`。
- 限制请求体大小、请求频率、并发和处理超时。
- 回调响应必须符合平台协议；业务暂时失败时应按平台重试机制安全处理。
- 对签名错误、重复事件、未知订单、金额不符、商户不符、过期通知分别测试。
- 不得把验签失败的回调标记为成功，不得仅凭客户端支付结果确认收款。

## 4.4 秘密和加密密钥管理

扫描所有配置、代码、前端构建变量、日志、测试文件和历史提交可见文件中的疑似秘密。

- 生产秘密从环境变量或受控秘密管理系统注入。
- 禁止秘密进入 Vue/小程序包、公开 API、错误消息或日志。
- 对不同用途使用独立密钥：会话签名、数据加密、人脸加密、Webhook、第三方支付等不得无理由共用。
- 检查密钥长度、随机性、编码和启动校验。
- 实现或完善密钥版本标识、轮换、旧密钥解密过渡和撤销流程。
- 加密失败时 fail closed，禁止静默降级为明文存储。
- 为密钥缺失、错误、轮换、旧数据解密和备份恢复编写测试与运维文档。
- 如发现已提交的真实密钥，不要在报告中复述；标记泄露类型并要求在平台轮换/撤销。

# 五、P0/P1：支付、退款、订单与财务账本

## 5.1 建立统一订单状态机

梳理订单从创建、待支付、支付处理中、已支付、制作中、待取餐/配送、完成、取消、退款申请、退款处理中、部分退款、全额退款、退款失败的全部状态。

先形成状态转换表，明确：

- 允许的状态转换；
- 触发角色/系统事件；
- 前置条件；
- 数据库事务边界；
- 外部平台调用；
- 幂等键；
- 失败恢复和补偿动作。

要求：

1. 禁止任意接口直接写入任意订单状态。
2. 所有状态转换通过统一领域服务或等价的集中机制执行。
3. 使用条件更新、乐观锁/版本号或行锁，避免并发覆盖。
4. 状态变更必须记录操作来源、操作者、时间、原因和关联事件，敏感字段脱敏。
5. 不允许客户端自行决定订单金额、支付成功、退款成功或财务状态。
6. 为非法状态跳转、并发操作、重复请求和超时恢复编写测试。

## 5.2 微信支付

重新核实项目实际采用的微信支付 API 版本和 SDK，并以对应官方协议为准。

检查并修复：

- 回调签名使用正确平台证书/公钥及官方算法；
- 对加密资源按协议解密，并校验必要的商户号、应用身份、交易状态、商户订单号、交易号、金额和币种；
- 对协议规定必需的字段，缺失即拒绝，不能仅在字段存在时比较；
- 金额使用整数最小货币单位或 Decimal，禁止 float 金额比较；
- 本地订单必须存在、属于正确商户/门店、金额一致、币种一致；
- 交易号和回调事件具有数据库唯一约束；
- 重复回调返回符合平台要求的响应，但不重复记账、发券、加积分或触发制作；
- 证书更新、平台证书轮换、时钟偏差和密钥配置有安全处理；
- 主动查单与异步回调并发到达时，只能产生一次有效支付确认。

不得为了让测试通过而跳过验签。单元测试使用官方格式的虚构密钥/测试证书或 mock，不使用生产密钥。

## 5.3 支付宝支付

按项目实际使用的支付宝接口版本和官方 SDK 核实：

- RSA2 验签必须覆盖平台规定的参数和规范化流程；
- 校验应用身份、商户身份（如该接口协议要求）、商户订单号、支付宝交易号、交易状态、金额、币种；
- 明确哪些成功状态可确认收款，不能把任意非失败状态视为成功；
- 回调金额必须与服务端订单应付金额精确一致；
- 支付宝交易号、商户订单号及回调事件建立正确唯一约束；
- 重复通知、并发通知和主动查单保持幂等；
- 私钥不得暴露给前端、日志、错误响应或仓库；
- 证书模式与公钥模式不得混用，配置必须与实际 SDK/接口模式匹配。

## 5.4 统一支付幂等与账务

设计并落实支付流水、退款流水、财务账本和订单状态的约束。

- 使用数据库唯一约束防止同一外部交易重复入账。
- 幂等键必须稳定、来源明确，不能只依赖进程内缓存或 Redis 锁。
- 在事务中完成本地支付状态、流水、账本和需要原子完成的本地权益变更。
- 外部网络调用不要在长事务中持有数据库锁；使用明确的处理中状态、任务/outbox 或可靠补偿流程。
- 明确支付平台已成功但本地落库失败、请求超时但平台已受理、查单与回调竞态的恢复方式。
- 对账任务应能发现平台成功而本地未成功、本地成功但平台不匹配、金额差异、重复流水和长时间处理中记录。
- 对账只能生成可审计的修复任务或按明确安全规则修复，不能静默改账。
- 财务记录应可追溯、不可被普通业务接口随意覆盖或删除。

## 5.5 退款

- 退款前验证订单归属、原支付成功、可退余额、已退款金额和操作权限。
- 防止并发退款导致累计退款超过实付金额。
- 使用退款请求唯一商户退款单号及外部退款号约束。
- 区分退款申请、平台受理、退款成功、退款失败和结果未知。
- 超时不得直接当作失败并重复发起新退款；先按官方接口查单或使用同一幂等标识重试。
- 部分退款和多次退款必须正确累计，禁止超过原支付金额。
- 退款成功后，按业务规则处理优惠券、积分、会员余额、库存、厨房任务和外卖平台订单。
- 所有人工退款操作记录操作者、原因、审批（若项目具备审批机制）和审计日志。
- 编写重复退款、并发退款、部分退款、回调乱序、超时及失败补偿测试。

## 5.6 优惠券、积分、会员余额

- 检查发放、领取、锁定、核销、撤销、退款返还和过期状态机。
- 使用账本/流水，不通过直接覆盖余额掩盖历史变化。
- 对每次发券、积分增减、余额变化设置业务幂等键和数据库唯一约束。
- 下单时锁定/预占优惠券；支付失败、超时或取消时按规则释放。
- 核销必须验证用户、门店、有效期、适用餐品、最低消费、叠加规则和使用次数。
- 退款后按明确业务规则计算优惠券与积分返还，防止套利和重复返还。
- 所有折扣和应付金额由后端重新计算，客户端金额仅作为展示。
- 使用 Decimal 或整数分计算，明确舍入规则并测试边界金额。

# 六、P0/P1：认证、授权与多门店隔离

## 6.1 建立后端统一授权策略

逐个检查全部 API 路由，不允许仅依靠 Vue 菜单、路由守卫或小程序页面控制权限。

为每个接口明确：

- 是否公开；
- 是否需要登录；
- 需要的角色/权限；
- 允许访问的门店范围；
- 资源所有权校验；
- 是否涉及敏感数据或财务操作。

实施：

1. 用户身份从已验证的服务端会话/令牌取得，不能信任客户端传入的 user_id、role、store_id。
2. 对订单、顾客、优惠券、菜品、员工、财务、图片、导出文件等资源执行对象级授权。
3. 所有门店范围从当前身份的授权关系中解析，并在数据库查询/更新时落实。
4. 防止通过修改 URL、JSON、Header、订单号、顾客 ID、门店 ID实现 IDOR/BOLA 越权。
5. 对跨门店管理员、总部角色和门店员工定义明确、可测试的授权矩阵。
6. 防止普通管理员给自己提权、创建更高权限账号、修改角色权限或绕过审批。
7. 对角色/权限变更、员工离职、门店解绑和令牌撤销及时失效缓存与会话。
8. 对导出、打印、图片、附件和 WebSocket 同样执行权限校验。
9. 统一 401/403 响应，不泄露资源是否存在等不必要信息。

## 6.2 多门店数据模型和查询

逐表检查订单、菜单、规格、价格、库存、顾客、会员、优惠券、员工、财务、外卖绑定、厨房任务和打印任务。

- 识别必须具有 store_id 的门店归属数据，以及明确属于总部/全局的数据。
- 对门店级资源建立必要的外键、索引、唯一约束和一致性检查。
- 组合唯一约束应包含正确的租户/门店维度，避免不同门店数据冲突。
- 任何通过资源 ID读取或修改门店数据的服务，都必须验证门店归属。
- 不允许仅在列表接口过滤门店，而详情、更新、删除、导出或统计接口漏掉过滤。
- 防止将其他门店的价格、库存、顾客、订单和财务信息返回给当前门店用户。
- 明确总部跨门店查询权限，并对敏感操作留审计记录。
- 增加至少两个门店、多个角色的越权集成测试。

## 6.3 顾客身份和账号绑定

- 将内部 customer/member ID 与微信 OpenID、UnionID（若适用）、支付宝用户标识、人脸身份分别建模。
- 登录凭证必须由后端通过平台服务端接口验证，不能信任客户端自报身份。
- 账号绑定必须要求当前账号已认证，并验证待绑定平台身份的控制权。
- 防止同一平台身份绑定多个不允许的会员，防止未经授权合并会员。
- 匿名顾客升级会员时，明确订单、优惠券、积分、口味偏好和授权记录的迁移规则。
- 对微信和支付宝身份不能简单按昵称、手机号或人脸相似度自动合并。
- 解绑、注销、换绑和账号找回需要验证、审计和数据处理规则。
- 增加重复授权、身份冲突、跨用户绑定、匿名升级和并发绑定测试。

# 七、P0/P1：人脸识别、隐私与个人信息保护

## 7.1 拆分人脸功能开关和授权

重新检查实际配置，尤其是人脸迎宾默认关闭但未知访客抓拍默认开启的组合。

将以下能力分别控制并在后端强制执行：

- 摄像头接入/采集；
- 人脸检测；
- 特征提取；
- 人脸身份比对；
- 未知访客抓拍；
- 原始图片存储；
- 迎宾语音播报；
- 与会员、订单关联。

不得因启用一个功能自动启用其他功能。未满足适用法律、平台规则及业务授权条件时，停止相应采集和处理。提供清晰告知、授权/拒绝、撤回、删除和人工处理流程。不得将默认开启当作有效授权。

## 7.2 数据最小化、保留和删除

- 分别定义原始图片、人脸模板/向量、识别事件、授权记录和审计日志的目的、访问权限与保留期限。
- 核查配置中的访客保留天数是否真正由清理任务执行，而非仅有配置项。
- 清理任务必须安全、可重试、可观测，并有删除结果记录；不得因任务失败无限保留。
- 实现顾客撤回授权、注销、删除请求和数据导出/查询流程（按适用要求）。
- 删除/匿名化时处理主库、对象存储、缓存、搜索索引和备份到期策略。
- 限制人脸数据查看、下载和导出，记录访问审计。
- 禁止将人脸原图或向量写入普通应用日志、错误跟踪或第三方分析系统。
- 保护上传目录，禁止通过猜测静态 URL访问敏感图片；使用鉴权下载或短期签名 URL。
- 对图片进行格式、大小、内容和解码安全校验，防止恶意文件上传。

## 7.3 加密、密钥轮换和活体检测

- 核实实际加密算法、随机 nonce/IV、认证标签、AAD 和密钥版本存储方式。
- 采用成熟加密库和经过认证的加密模式；禁止自创加密算法。
- 防止 nonce 重用；错误密钥、篡改密文和认证失败必须拒绝解密。
- 轮换密钥时支持受控旧密钥读取与迁移，禁止无保护明文降级。
- 对活体检测核实其真实实现和供应商能力；配置名称或 challenge 模式不等于可靠活体能力。
- 对照片、屏幕重放、视频重放、过期挑战、重复挑战和接口直接提交特征进行授权范围内测试。
- 人脸匹配不能作为支付授权、资金转移或高风险账户操作的唯一认证因素。
- 记录阈值、模型版本、错误率评估和人工复核流程，避免误识别直接合并身份或泄露会员信息。

# 八、P1：微信和支付宝小程序全流程

## 8.1 登录与首次扫码

分别逐页、逐接口检查微信与支付宝：

- 扫码进入、分享进入、冷启动、会话过期和重新登录；
- 平台登录 code 的服务端验证、会话创建、过期和撤销；
- 未授权浏览菜单、选择门店、加购和提交订单的业务规则；
- 匿名购物会话与正式会员的生命周期；
- 首次授权、拒绝授权、授权撤回和账号切换；
- 门店、桌台、购物车和用户身份切换时的数据清理；
- 防止使用客户端伪造的用户 ID、OpenID、支付宝 ID、门店 ID和价格。

不得在用户未明确同意或业务无必要时过早创建永久会员或采集敏感资料。若匿名会话是业务需要，应使用随机、不可猜测、可过期的服务端会话标识，并限制其权限与数据保留。

## 8.2 购物车、下单和库存

- 购物车中的菜品、规格、加料、数量、价格和门店信息均由后端重新校验。
- 菜品下架、价格变化、规格失效、库存不足时，提交订单应明确提示并阻止错误下单。
- 门店或桌台切换必须清空或隔离旧购物车，避免跨门店混单。
- 防止快速连点、网络重试、页面重入和请求超时造成重复订单。
- 设计下单幂等键，并在数据库层保证唯一性。
- 明确下单时库存预占、支付成功扣减、取消释放和退款回补策略，确保与堂食/外卖共享库存策略一致。
- 后端计算所有金额、优惠和应付金额。
- 测试弱网、断网恢复、重复提交、支付中退出、后台切换、应用重启和会话过期。

## 8.3 微信/支付宝支付客户端

- 支付参数只能由后端根据已验证订单生成。
- 客户端支付成功回调仅用于触发服务端查单/刷新，不可直接把订单写为已支付。
- 处理用户取消、支付失败、支付处理中、重复回调、网络超时、应用退出和重新进入订单页。
- 订单结果以服务端核实的支付状态为准。
- 防止支付成功页重复发券、积分或创建厨房任务。
- 检查微信和支付宝 API 的平台差异，禁止将一个平台的参数或状态码直接套用到另一个平台。
- 增加模拟器/自动化测试，并提供真实沙箱或小额测试验收步骤；不得用生产真实资金进行自动化测试。

## 8.4 用户体验与异常状态

统一并检查加载、空状态、错误提示、重试、按钮防重复、登录失效、门店关闭、营业时间、菜品售罄和服务端维护状态。

所有用户提示应准确，不得显示“支付成功”而服务端尚未确认。错误信息不得包含堆栈、SQL、密钥或内部服务器信息。

# 十、P1：数据库迁移、模型、事务和数据完整性

## 10.1 Alembic/迁移链

- 自动检查迁移 head、父版本、分支和循环。
- 从空数据库完整升级到当前版本。
- 从上一可用版本的脱敏测试备份升级到当前版本。
- 对模型与数据库 schema 做差异检查。
- 检查重复字段/索引、缺失索引、错误默认值、NULL 语义、字段长度和字符集。
- 迁移不得悄悄删除数据或重置业务表。
- 对大表索引、字段类型变更和回填评估锁表、执行时间和磁盘空间。
- 需要时使用分阶段迁移：先兼容新增、再回填、再切换读写、最后清理旧字段。
- 明确哪些迁移可逆；不可逆迁移必须说明备份和恢复方案。
- 生产迁移前执行备份、检查备份可恢复性和变更审批。
- 不得为了通过迁移测试删除历史迁移或修改已发布迁移的语义；如需修复，新增后续迁移。

## 10.2 数据库约束和事务

- 对业务唯一性建立数据库唯一约束，不仅依赖 Python 先查后写。
- 对金额、数量、状态和外键增加适当的 CHECK/外键/非空约束（结合实际 MySQL 版本支持情况）。
- 检查所有多表写操作的事务边界。
- 避免在事务中进行慢速外部 HTTP 调用。
- 统一处理死锁、锁等待超时和可安全重试的事务。
- 对事务重试使用幂等机制，避免重复执行外部副作用。
- 检查删除策略、软删除、历史订单和财务流水保留要求。
- 检查时区存储与查询，统一存储 UTC 时间，明确门店 IANA 时区用于营业日、排班、报表和定时任务；不能用固定偏移替代夏令时规则。
- 为订单号、支付流水、退款单号、库存流水和审计事件设置正确索引。

# 十一、P1：库存、厨房 KDS、打印与外卖平台

## 11.1 库存和菜单一致性

明确并实现库存来源与扣减策略：

- 门店总库存；
- 堂食可售库存；
- 各外卖平台渠道库存；
- 安全库存/缓冲量；
- 预占库存、已售库存、取消释放和盘点调整。

要求：

1. 所有库存变更通过统一库存服务或领域接口，禁止不同模块各自直接修改库存。
2. 使用原子扣减和数据库约束防止超卖。
3. 每次库存变更记录来源、门店、餐品/规格、数量前后值、原因、关联订单/平台事件和操作者。
4. 明确平台同步延迟、失败重试、限流和最终一致性策略。
5. 同步失败不能静默丢失；必须有待重试队列、死信/失败记录、告警和人工重放工具。
6. 防止重复外卖回调重复扣库存。
7. 菜品下架、售罄、价格变更和规格变更必须有清晰的本地与平台同步策略。
8. 对“最后一份库存”并发购买、平台回调乱序、断网恢复和补偿做测试。

## 11.2 KDS 厨房显示

- 厨房任务只由服务端已确认的有效订单状态生成。
- 任务生成具备幂等性，不能因支付回调重试产生重复制作单。
- 明确堂食、外卖、退款、取消、加单、退菜和部分完成的任务状态机。
- KDS 的门店、档口、角色和设备必须经过服务端授权。
- WebSocket 断线后可通过服务端可靠补拉，不能只依赖内存事件。
- 事件应有可排序的 ID/版本或可靠时间信息，处理重复、乱序和漏消息。
- 打印失败、厨房设备离线和重连应有状态提示及人工补打，防止重复出单。
- 订单取消/退款后，按业务规则通知厨房，不得静默删除已经制作的记录。
- 增加重复事件、断线重连、消息乱序、设备离线和跨门店测试。

## 11.3 美团/饿了么适配

逐个检查现有平台适配器和商户绑定逻辑，不得凭空假设平台 API。

- 每个外部平台店铺与内部 store_id 建立明确、唯一且可审计的绑定。
- 平台应用凭证按门店/商户安全保存和轮换，不向客户端暴露。
- 菜品、规格、价格、图片、库存、上下架状态建立字段映射和同步版本。
- 对外部订单号建立平台维度唯一约束，处理重复推送和乱序通知。
- 验签、时间戳、事件 ID、重放防护按平台官方协议实现。
- 平台订单状态与内部订单状态使用显式映射，未知状态不能被默认为成功。
- API 限流、超时、重试、退避、熔断和平台故障要有明确策略。
- 同步任务记录请求摘要、响应状态、重试次数和错误分类，敏感字段脱敏。
- 提供差异对账、失败重放和人工修复入口，并验证权限。
- 未有正式商户凭证或官方文档时，完成适配层、mock 和接口契约测试，但将真实联调标记为待验证，禁止伪造联调成功。

## 11.4 打印

- 检查打印模板注入、设备认证、门店隔离和敏感字段。
- 打印任务具备唯一任务 ID、幂等和可追踪状态。
- 设备离线、超时、失败、重复请求和人工补打必须有明确处理。
- 防止普通用户伪造打印任务或打印其他门店订单。
- 不在日志中保存不必要的顾客手机号、地址和支付信息。

# 十二、P1/P2：性能、并发、缓存与后台任务

## 12.1 数据库连接池和 Gunicorn

核查实际部署 worker 数、每进程连接池、最大溢出、后台任务连接和 MySQL max_connections。

- 计算总连接上限并确保留有运维余量。
- 避免 worker 数量与连接池配置相乘后耗尽数据库连接。
- 检查连接泄漏、长事务、慢查询、N+1 查询和缺失索引。
- 设置合理的连接超时、池等待超时、回收和健康检查。
- 对连接池耗尽、数据库不可用和恢复过程进行测试。
- 不得仅通过无限增加连接数解决性能问题。

## 12.2 并发与竞争条件

至少构造以下自动化测试：

- 多用户同时购买最后一份菜品；
- 同一订单并发支付确认；
- 同一订单并发取消和支付回调；
- 同一订单并发退款；
- 同一优惠券并发领取/核销；
- 同一会员并发积分消费；
- 同一库存由堂食和多个外卖渠道同时扣减；
- 同一平台事件重复、乱序到达；
- 定时任务重复启动或多个 worker 同时执行。

使用真实数据库集成测试验证锁、唯一约束和事务，不得只用内存 mock 证明数据库并发安全。

## 12.3 Redis、任务队列和定时任务

- 明确 Redis 故障时每个功能的降级行为。
- 不得将 Redis 锁作为资金幂等的唯一保障。
- 对任务设置唯一业务键、重试上限、退避、超时、失败队列和告警。
- 任务处理要可重入、幂等、可追踪。
- 防止多个 worker 重复执行清理、结算、优惠券发放和库存同步。
- 检查任务时区、夏令时、跨日营业和补跑逻辑。
- 对任务积压、执行失败和重复执行提供监控。

# 十三、P2：口味推荐、会员运营与数据正确性

针对多面、多麻、多辣、少麻、少辣、不要麻、不要辣等偏好：

- 区分顾客明确设置的偏好和算法推断偏好。
- 明确订单取消、退款、赠品、多人拼单和代点订单是否纳入计算。
- 按顾客、门店、菜品、规格和时间建立合理数据关联。
- 不得将一次订单推断为永久、确定的个人偏好。
- 推荐结果需可解释、可关闭、可重置，并允许顾客修改。
- 避免将敏感个人信息用于未经授权的画像。
- 检查时区和星期计算，按门店/用户适用时区计算用餐时段，避免 UTC 日期导致星期错误。
- 对新用户冷启动、数据不足、偏好冲突和历史数据缺失提供回退逻辑。
- 推荐算法不得影响后端价格、支付金额或未经确认自动下单。
- 增加算法单元测试、边界测试和脱敏样例验证。

# 十四、P1/P2：日志、监控、备份和部署

## 14.1 日志与审计

- 使用统一结构化日志，包含 request_id/trace_id、业务对象 ID（非敏感）、模块和错误分类。
- 对密码、令牌、Cookie、支付签名、私钥、身份证信息、人脸数据、手机号和地址按需脱敏。
- 区分业务审计日志和调试日志，限制访问权限和保留期限。
- 关键财务、权限、门店配置、退款、数据导出和隐私操作必须记录审计事件。
- 日志失败不得导致核心业务状态被错误确认。
- 检查异常处理是否吞掉异常、只打印后继续或返回虚假成功。

## 14.2 监控和告警

为以下指标增加可用监控或明确集成点：

- API 请求量、错误率、延迟和超时；
- 数据库连接池使用率、慢查询、死锁和连接失败；
- 支付成功/失败/处理中/对账差异；
- 退款积压和失败；
- 库存同步失败、超卖告警和平台差异；
- Webhook 验签失败、重复事件和处理延迟；
- 后台任务积压、重试和死信；
- KDS/打印设备在线状态；
- 人脸服务错误率、采集开关和数据清理任务结果。

不得将顾客敏感数据作为监控标签，避免高基数标签和敏感信息泄露。

## 14.3 备份与恢复

- 提供数据库和必要对象存储的备份策略、加密、保留期限和权限说明。
- 明确 RPO/RTO 目标及其由业务方确认的状态。
- 编写并验证恢复演练流程，不能仅确认备份文件存在。
- 检查迁移失败回滚、备份恢复后密钥可用性、支付/库存对账和任务恢复。
- 备份不得长期保存不必要的人脸原图或秘密明文。
- 不得在未获授权的生产环境执行恢复覆盖。

## 14.4 依赖与部署

- 检查 Python、Node、Vue、小程序构建依赖的锁文件和版本可重复性。
- 执行可用的依赖漏洞扫描，并记录工具、数据库更新时间和结果。
- 移除未使用或高风险依赖前先确认调用关系和兼容性。
- 检查 CORS、Trusted Host、HTTPS、Cookie 安全属性、CSRF（适用时）、安全响应头、上传目录和静态文件权限。
- 生产调试模式关闭，错误页面不暴露堆栈。
- 检查 Nginx 代理头、请求体大小、超时、限流和 WebSocket 配置。
- 检查容器/进程用户权限、文件权限、日志轮转和服务重启策略。
- 不得未经用户授权改动生产服务器或执行部署。

# 十五、必须新增或完善的自动化测试

根据项目当前测试框架补齐测试，不要为了方便另起一套与现有架构冲突的测试体系。

## 15.1 后端单元测试

至少覆盖：

- 订单状态机所有合法/非法转换；
- 金额、折扣、税费/配送费（若适用）和舍入；
- 支付/退款状态解析与验签失败；
- 幂等键和重复事件；
- 门店权限和对象级授权；
- 优惠券、积分、会员余额；
- 库存扣减、释放和回补；
- 人脸配置、加密、密钥版本及保留策略；
- 时区、营业日和定时任务边界。

## 15.2 API 集成测试

至少覆盖：

- 未登录、令牌过期、权限不足；
- 跨门店读写、越权导出和文件访问；
- 无效参数、超大请求体、重复提交；
- 支付成功、失败、重复、乱序、金额不符、商户不符；
- 退款并发和结果未知；
- 平台回调签名失败和重放；
- 数据库事务回滚和唯一约束冲突。

## 15.3 前端与小程序测试

为现有工具链可支持的范围增加：

- Vue 核心页面和权限行为测试；
- 微信/支付宝登录、授权拒绝、会话过期；
- 门店切换、购物车隔离、菜品下架和库存不足；
- 重复提交、支付取消、支付处理中、重新查询；
- 错误提示不误报支付成功；
- 页面退出重进、弱网重试和重复点击。

## 15.4 测试数据与安全

- 使用完全虚构的用户、订单、密钥和平台响应。
- 不复制真实顾客数据到测试环境。
- 测试日志不得输出秘密。
- 测试必须能重复执行，清理自己创建的数据，不得删除共享或生产数据。
- 外部平台使用 mock/沙箱，明确区分模拟测试与真实平台联调。

# 十六、执行顺序与每阶段交付

按以下顺序实际执行，不要只生成任务列表：

### 阶段 A：基线与 P0

1. 生成项目地图、问题台账和测试基线。
2. 修复生产默认秘密、配置校验、叫号屏和 Webhook 安全。
3. 修复认证、权限、对象级授权和跨门店越权。
4. 修复支付验签、订单状态机、支付幂等、账务和退款安全。
5. 为每项修复增加测试并运行。

### 阶段 B：数据库与核心业务

1. 检查并修复模型、迁移链、索引、唯一约束和事务。
2. 修复库存、优惠券、积分和会员身份一致性。
3. 验证空库迁移和上一版本升级。
4. 执行并发与故障恢复测试。

### 阶段 C：各客户端

1. 修复 Vue 后台认证、权限、状态和异常处理。
2. 修复微信小程序登录、购物车、下单和支付流程。
3. 修复支付宝小程序对应流程并验证平台差异。
4. 确保三端的服务端业务规则一致，不能由客户端绕过。

### 阶段 D：人脸、外卖、KDS 和打印

1. 修复人脸授权、采集开关、加密、保留和删除。
2. 修复多门店菜单、库存和外卖平台映射。
3. 修复平台事件幂等、重试、对账和失败恢复。
4. 修复 KDS、WebSocket、打印和补打状态。

### 阶段 E：性能、部署和最终验收

1. 执行依赖扫描、静态检查、前端构建和小程序构建（环境允许时）。
2. 执行完整测试套件、数据库迁移测试和并发测试。
3. 检查所有修改的 diff、秘密泄露、临时文件和调试代码。
4. 更新文档、部署说明、环境变量说明和故障恢复手册。
5. 生成最终审计与验收报告。
