# SmartNoodleHouse 审计问题归纳与跨项目预防措施

> 整理日期：2026-11-08
> 用途：将本项目多轮代码、依赖、数据库、部署、文档和本机同步审计中暴露的真实问题与高风险检查类别，整理成其他项目可复用的预防规则。
> 重要边界：本文件严格区分“本轮有证据的问题/差异”和“必须检查的通用风险”。通用检查项不代表当前项目已经存在漏洞；本机历史差异也不等于 GitHub main 存在相同缺陷。

## 1. 已有证据的问题与修正

| # | 审计发现/差异 | 证据与影响 | 本项目处理/当前结论 | 其他项目预防规则 |
|---|---|---|---|---|
| 1 | 文档技术栈与实际工程不一致 | 后台手册曾描述 PostgreSQL/SQLite、Taro；当前工程事实为 MySQL 8.x、Vue 3 + Vite、微信/支付宝两个独立小程序目录。会导致开发者选错驱动、命令和构建工具 | 已在后台手册加入技术栈勘误；其他专题文档加上当前代码为准的说明 | 每次技术栈变化必须全仓库搜索旧术语；README、AGENTS、部署、操作、CI、教程一起更新 |
| 2 | 文档把项目描述为“已上线” | 营销实施方案中出现“已上线能力”表述，与项目实际仍处于上线前开发/集成/验收阶段不符 | 已改为“当前主线实现”，并强调未验收功能不能称为已上线 | 项目状态统一定义；将已实现、已验证、待验证、规划中、外部阻塞分开 |
| 3 | 专题文档出现具体叫号屏访问令牌 | KDS 文档曾含可直接复制的 token 字符串，可能造成访问凭据泄漏 | 已在文档分支替换为占位说明；若曾真实有效必须轮换，删除文本不等于令牌失效 | 全仓库 secret scan + 人工审查 Markdown、截图、命令示例、日志；只写变量名，不写值 |
| 4 | README 包含开发默认管理员凭据描述 | 将固定账号/密码放在入口文档会诱导生产沿用 | 新 README 不再展示固定默认密码，改为通过初始化管理员流程安全设置 | 禁止文档/种子/镜像使用可预测管理员密码；首次启动强制初始化高熵凭据 |
| 5 | 历史配置清单被误认为当前实时结论 | 配置检查文档来自 2026-10 的特定本机快照，P1/P2 数量和环境值可能已变化 | 已标记为历史快照，要求每个目标环境重新核验并保存脱敏证据 | 每份检查报告记录日期、commit、环境和范围；历史结果不覆盖当前状态 |
| 6 | 历史测试报告与当前主线测试证据混淆 | 旧报告有 799 collect / 791 passed / 8 skipped 等统计，不能代表当前 main | 已保留为历史归档，并追加 2026-11-08 本机前端/Rust结果及未覆盖范围 | 所有测试报告必须绑定 commit SHA、平台、运行时、命令、通过/失败/跳过数 |
| 7 | 前端构建成功仍有大 chunk 警告 | 本机 Vite 构建成功，但入口 JS chunk 约 891.98 KB，超过 500 KB warning | 记录为性能优化项，不误报为构建失败 | CI 将错误与 warning 分开；warning 必须评估影响、登记责任人和优化目标 |
| 8 | 依赖树包含可选依赖缺失和多版本重复 | npm ls 输出 UNMET OPTIONAL DEPENDENCY、传递依赖重复；不等同于项目直接依赖未安装或源码重复引用 | 本机重复导入检查扫描 195 文件通过，依赖使用审计 94 文件/13 直接依赖通过 | 区分 optional、peer、transitive、direct；结合 lockfile、源码 import、动态加载和实际构建判定 |
| 9 | 本机 Node/npm 与 CI pin 不一致 | 本机最初 npm 11.9.0，CI pin 为 11.19.1；会造成 lockfile 或 npm 行为漂移 | 本机已安装 npm 11.19.1；Node 24.14.0 用于本次本机测试 | 运行时和包管理器版本写入 CI 与开发文档；执行 npm ci/locked build |
| 10 | 本机 SQL 文件与 main schema 有明显差异 | 本机旧 struct/data_sys 曾缺失 leader_fencing_state、event_fingerprint、sync_version、门店菜单生成字段、对账门店范围等，并存在重复表定义/外键差异 | 本机旧修改已备份后同步 main；当前工作区与 main 完全一致。旧 SQL 只留在受保护备份，不应再合并回主线 | SQL 变更逐表比较 canonical schema、迁移链、索引、外键、唯一约束和种子脚本；禁止简单拼接两个 DDL |
| 11 | 本机旧 SQL 中出现硬编码数据库账号凭据 | 本机未提交 SQL 修改和备份 patch 含疑似真实凭据；未作为本轮主线变更提交 | 本机已同步 main；备份文件仍需妥善保护。若凭据真实/曾使用，必须轮换数据库账号密码 | secret scan 覆盖工作区、stash、patch、bundle、备份和 Git 历史；凭据泄漏先轮换再清理 |
| 12 | 历史审计资料可能保留过期分支、绝对路径和旧迁移编号 | 历史报告/提示词不一定对应当前 main，直接执行会重复修复或破坏现有实现 | 已为多份专题文档加入当前主线复核提示 | 每个 AI 提示词必须先 fetch 最新主线、检查现有实现、避免重复开发和无证据改动 |

## 2. 本机验证结果（证据范围）

维护者提供的 Windows 本机输出（2026-11-08）：
- npm 11.19.1；npm ci 成功；npm audit 0 vulnerabilities。
- 重复导入检查 195 个 JS/TS/Vue 文件通过。
- 依赖使用审计 13 个直接依赖、94 个源码/配置文件通过。
- Vitest 3 个文件、14 项测试通过。
- vue-tsc + Vite 构建成功；存在 891.98 KB 入口 chunk warning。
- Rust cargo metadata --locked 成功；7 项测试通过；benchmark target 成功；release DLL 构建成功，282,624 bytes。

未由上述输出证明：Python 全量测试、真实 MySQL/Redis 集成与故障注入、双端小程序构建/真机支付、外卖真实沙箱、摄像头现场验收、Ubuntu 生产部署、备份恢复、监控和回滚。不得将其标记为已通过。

## 3. 通用高风险检查项（不是当前缺陷结论）

### 3.1 依赖和构建
- 直接依赖是否真实使用、动态依赖是否遗漏、同一职责是否重复实现。
- manifest/lockfile/CI pin 是否一致；Windows/Linux/Python/Node/Rust 兼容矩阵是否真实验证。
- 依赖漏洞、许可证、维护状态、弃用 API 和供应链风险是否有官方证据。
- 大 bundle、长构建、CI job 长时间挂起是否有量化原因。

### 3.2 数据库与字符集
- canonical schema 与 migration 是否漂移；初始化 SQL 是否误删生产数据。
- 外键、唯一索引、复合索引、NULL、默认值、时区、金额精度是否匹配业务。
- MySQL utf8mb4 是否覆盖连接、表、列、迁移和导入导出；是否存在乱码/双重编码。
- 并发写、迁移锁表、数据回填和失败恢复是否经过真实数据库验证。

### 3.3 Redis 与分布式系统
- 缓存穿透：非法 ID、高频不存在资源、空值缓存和参数校验。
- 缓存击穿：热点 key 同时失效、single-flight、互斥重建和逻辑过期。
- 缓存雪崩：TTL 抖动、分批过期、预热和故障恢复限流。
- 锁：owner token、原子释放、租约、续租、锁过期旧持有者、fencing token。
- 限流：Redis 不可用时 fail-open/fail-closed 是否按接口风险配置。
- 多实例任务：leader 选举、租约、任务幂等、超时回收、死信和重放。
- 网络分区、主从切换、连接池耗尽、重连风暴、慢查询和内存淘汰。

### 3.4 业务资金与一致性
- 支付回调验签、商户/金额/币种校验、重放保护、重复和乱序通知。
- 退款上限、部分退款、并发退款、组合支付和回调未知态。
- 库存原子扣减、取消回补、活动抢购防超卖和幂等。
- outbox/inbox、账本分录、对账、补偿任务和人工纠错审计。

### 3.5 多租户与隐私
- 每条 API、任务、缓存、WebSocket、文件、导出和报表是否隔离。
- 总部/租户覆盖规则是否定义业务键和唯一约束。
- 人脸、定位、手机号、支付信息是否按最少必要、主动授权、加密、可撤回和删除处理。

## 4. 其他项目必须落地的预防机制

1. 在项目根目录维护唯一 README 和文档索引。
2. 建立通用问题台账：证据、影响、根因、修复、测试、责任人和关闭条件。
3. CI 设置依赖锁、静态检查、单测、真实数据库/缓存集成、迁移和构建门禁。
4. 每个关键业务设计失败路径：重复、超时、乱序、并发、网络中断、服务恢复。
5. 每次上线前演练备份恢复、数据库迁移、密钥轮换、灰度和回滚。
6. 文档随代码 PR 更新；每季度复核过期链接、版本、命令和配置。
7. 安全凭据泄漏事件必须先撤销/轮换，后清理历史和部署副本。
8. 不允许用“增加代码/测试数量”替代实际风险闭环。
