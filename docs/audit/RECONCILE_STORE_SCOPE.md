# 支付对账与历史订单归档的门店数据隔离

## 作用域约定

- scope_store_id = 0：总部/平台级对账，旧版本已存在的批次迁移后均归入此作用域。
- 正数 scope_store_id：指定门店的独立对账批次。
- 对账批次唯一键为 (channel, bill_date, scope_store_id)，同一天同渠道可分别存在总部和不同门店的批次。
- 总部账号不传 store_id 时执行全平台对账；总部也可传门店 ID 查看/执行单店对账。
- 门店账号的 store_id 永远由服务端员工账号绑定信息决定，忽略客户端伪造的门店 ID；未绑定门店的非超管请求返回 403。
- 对账差异详情先验证批次作用域，跨门店或不存在的批次统一返回 404。

## 渠道账单导入

总部可以导入完整商户账单（不传 store_id），此时本地匹配覆盖全部订单与充值记录。

门店独立对账时，上传文件必须是已按门店过滤的账单行，并且每条账单必须包含商户支付单号（payment_no/out_trade_no）。服务端会按订单 store_id 或充值单 store_id 检查已知支付单归属；如果账单包含其他门店的支付单，或已知支付单无法确认门店归属，会拒绝导入。未在本地找到的支付单仍保留为 LONG 差异，供门店核查渠道侧孤儿交易。不能把同一商户号的完整总账单直接作为单店账单。

如支付平台只提供商户总账单，应由总部导入总账；不要让门店管理员自行把总账重复导入多个门店批次。

## 历史订单归档

- 总部可不指定门店归档全部门店。
- 门店管理员只归档自己的门店订单；传入其他门店 ID 不会扩大权限。
- 未绑定门店的非超管不能查询归档列表或执行归档。
- 归档仍为快照写入，不删除订单热表，避免破坏支付/财务等外键关系。

## 数据库升级与回滚

- 新安装：sql/struct.sql 已包含 scope_store_id 与复合唯一索引。
- 已安装数据库：执行 Alembic 0048_reconcile_store_scope，旧批次自动归入总部作用域 0。
- 降级仅在不存在同渠道/同日期的多作用域批次时允许；一旦有多个门店批次，迁移会拒绝降级，避免合并或丢失对账证据。


## 其他管理端数据范围

- 员工排队列表按登录账号绑定门店过滤；即使客户端伪造其他 store_id，也只能查询本店。
- 排队叫号、落座、取消操作在读取票据后再次校验票据所属门店；跨店票据统一返回 404，未绑定门店的员工返回 403。
- A/B 实验报表包含跨门店曝光、转化与归因 GMV，只有持有 system:manage 的平台管理账号可读取。
- 全局 API 性能指标同样要求 system:manage，不再由普通 order:read 员工权限开放。
