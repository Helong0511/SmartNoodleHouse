## 0. 执行摘要

这是一套**工程水位明显高于同类业务系统**的代码库：JWT 三类令牌 + `token_version` 撤销、`require_bound_store` 门店隔离、Redis Lua 原子锁 + DB fencing epoch、条件 `UPDATE ... WHERE stock >= qty` 防超卖、回调验签 + DB 唯一回执、outbox 同事务补偿、Nginx 安全头与反代头覆盖、生产启动校验，都做得相当扎实。

但本轮复核发现，**安全性高度依赖「`APP_ENV` 被正确设置」这一个前提**，而该前提本身是软默认值；一旦失效，支付 mock、回调跳过验签、mock 登录、docs 暴露、异常原文回显、密钥片段回显会**同时**打开。此外还发现一条**当前仍在持续发生的凭据泄露**（httpx INFO 日志明文打印微信 AppSecret），以及**发布态与部署流程上的两类硬阻断**（小程序占位符导致正式版白屏、生产部署文档照抄即删库）。

| 等级 | 数量 | 含义 |
|---|---|---|
| **P0** | 4 组 | 资损 / 凭据泄露 / 上线阻断 / 数据丢失，需立即处理 |
| **P1** | 22 条 | 高危，生产或特定条件下必现 |
| **P2** | 24 条 | 中风险、明显坏味道、一致性分叉 |
| **P3** | 10 条 | 建议性、死代码、可维护性 |

> 分级依据是「是否可直接造成资金/数据/权限损失」与「触发前提是否容易满足」，不按修复工作量排序。P0 中部分条目带**明确触发前提**（如生产 `.env` 漏配 `APP_ENV`），已在各条目内注明，请以「消除前提」而非「祈祷不触发」的方式处理。

### P0-1 生产配置校验存在单点失效：`APP_ENV` 默认 development，且校验只在 lifespan 内执行

**位置**：`backend/app/core/config.py:25`、`backend/app/core/config.py:221-226`、`backend/app/core/startup_checks.py:154`、`backend/app/main.py:244`、`backend/app/main.py:876`

```python
# config.py:25
app_env: str = "development"
# config.py:222

# startup_checks.py:154
```

**证据与连锁后果**：`validate_settings()` 仅在 `lifespan` 中调用（`main.py:244`），而 `create_app()` 在模块导入时执行（`main.py:876`），且已依 `is_development` 决定 `/docs`、`/openapi.json`（`main.py:766-768`）与 `/uploads` 挂载（`:870-871`）。因此生产 `.env` 漏写、拼错 `APP_ENV`（`producton` / `staging`），或 ASGI 以 `--lifespan off` 启动时，所有阻断项降级为 warning，以下路径同时打开：

- `payment_service.py:154-161` `_payment_mock_allowed()` 仅 `if s.is_production: return False`；`ALLOW_PAYMENT_MOCK=true` 时即便已配真实商户号仍返回 `_mock: True`（`:173-195`），`_settle_mock_payment()`（`:1648-1665`）直接置 `PAID` 并入账，**顾客可零元下单**，连带积分、券核销、出库、财务 SALE 全线触发；退款侧 `:260-265 / :414-419` 同样直接返回 SUCCESS。
- `payment_verify.py:61-65 / :234-238`：`_dev_simulate` 跳过微信/支付宝全部验签；`miniprogram_auth.py:36` `mock:` 登录码、`miniprogram_member.py:547` `mock:debug` 生效。
- `exceptions.py:146-147`：500 响应回显异常类型与 `str(exc)`，`:129-132` 回显 DB 原始错误（含主机/账号信息）。
- `settings.py:54 / :22-32`：`system:manage` 可拿到 `JWT_SECRET`、微信 `API_V3_KEY`、支付宝私钥的首尾片段。

**触发前提**：生产未显式设置 `APP_ENV=production`，或以 `--lifespan off` 启动。`.env.production.example:32` 已写 `APP_ENV=production`，正常部署不会触发——但这正是问题：**整套安全模型押在一个可静默失效的字符串上**。

**修复**：① 改为「显式 opt-in 开发」，仅 `development/dev/local` 放宽，未知值一律按生产校验；② `validate_settings()` 在 `create_app()` 开头同步调用一次；③ 增加与部署事实绑定的哨兵（已配置正式商户号、或非回环 DB 时强制按生产校验）；④ `_settle_mock_payment`、`_dev_simulate` 等关键旁路自带 `not is_production` 硬断言，不只靠启动检查。

### P0-2 httpx INFO 日志持续明文输出微信 AppSecret（凭据已落盘）

**位置**：`backend/app/core/logging_config.py:26-38`、`backend/app/services/wechat_mini_client.py:71-78`、`logs/backend/app5.log:27212`

```python

logging.getLogger("uvicorn.access").setLevel(logging.WARNING)
```

```
2026-10-24 17:14:18,939 INFO [httpx] HTTP Request: GET https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=wxd0964c5d02b1549d&secret=<32位真实密钥> "HTTP/1.1 200 OK"
```

**影响**：密钥以明文进入 stdout 与文件日志（仓库有 7 个 5MB 的轮转日志）。`logs/` 虽被 `.gitignore` 忽略，但运维打包日志、上传工单、云主机快照都会带出凭据；这与 `docs/audit/REMAINING_ISSUES.md:14` 的 **BLK-002「git 历史曾出现真实密钥，需全量轮换」** 直接呼应，说明该密钥很可能仍在有效期内。**当前代码路径仍会持续写入**，不是纯历史残留。

### P0-3 双端小程序发布态配置：占位符未替换即正式版白屏，且环境探测失败降级到 HTTP 内网

**位置**：`miniprogram-wechat/config/env.js:22,52-59,88-100`、`miniprogram-alipay/config/env.js:22,50-57,86-98`（两端共有）；`miniprogram-wechat/app.js:15`、`utils/api.js:4`

**两个独立后果**：
