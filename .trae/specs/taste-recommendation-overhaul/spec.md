# 顾客智能口味推荐系统系统性优化 - 产品需求文档

## Overview
- **Summary**: 在现有"规格级口味偏好"（订单衰减重算 + 季节/天气场景加权 + 加购预选规格）基础上，升级为覆盖"产品口味画像 → 多维顾客画像 → 产品级智能推荐 → 分类差异化调优 → A/B 实验与性能监控 → 隐私合规"的完整闭环，并落地微信、支付宝双端小程序。
- **Purpose**: 提升推荐精准度与采纳率（线上由 A/B 实验度量、离线由合成数据集验证），同时通过缓存与接口治理把小程序交互响应速度提升 40% 以上，满足《个人信息保护法》对个性化推荐与用户画像的合规要求。
- **Target Users**: ①堂食/外卖顾客（双端小程序使用者）；②门店店长/品牌运营（后台维护口味标签、查看推荐效果与 A/B 报表）。

## Goals
- 建立多维度顾客口味偏好模型：消费订单、规格选项、隐式行为（曝光/点击/加购/复购/移除/退款）、显式轻量评价、产品口味属性五维融合。
- 实现产品级"猜你喜欢"推荐：冷启动（无历史顾客）→ 温启动（少量行为）→ 热启动（成熟画像）三态平滑降级，任何状态下都有可展示结果。
- 产品口味画像（甜度/辣度/口感/风味等）自动推导并允许后台人工微调。
- 分类差异化：饮品/面/烘焙/小食等不同品类使用不同的召回排序权重，权重可配置。
- 持续学习：顾客交互后 5 分钟内完成画像更新（事件触发增量更新 + 5 分钟批处理兜底）。
- A/B 实验框架：稳定分流、曝光/采纳埋点、后台效果报表，支撑精准度 +30%、采纳率 +25% 的线上验证。
- 性能：推荐/菜单类接口 P95 < 500ms、顾客端首屏加载 < 2s、相对优化前基线响应耗时下降 ≥ 40%（离线/测试环境可度量，线上由监控持续观测）。
- 隐私合规：个性化推荐可一键关闭（关闭后退回非个性化热门榜且不再采集行为）、画像可查看可清除、行为数据留存期自动清理、个性化同意留痕。

## Non-Goals
- 不引入外部大数据/机器学习平台（Spark、Flink、向量数据库、第三方推荐 SaaS）；全部基于现有 MySQL + Redis + Python 进程内计算实现。
- 不做 LLM/大模型口味对话（沿用规则+统计模型，保证可解释、可离线复算）。
- 不改造外卖平台侧（美团/饿了么）的推荐与菜单逻辑。
- 不做强制星级+图文长评价体系；显式反馈仅限订单完成后的轻量标签评价。
- 本期不保证线上真实指标在交付当日即达到 +30%/+25%（需 2–4 周线上实验周期）；交付物为"度量能力 + 离线达标证据 + 线上实验位"。
- 不新增门店经营报表的财务分析模块，A/B 报表仅限推荐效果指标。

## Background & Context
- 现状后端：`CustomerPreference`（规格组+选项维度，`preference_score/order_count/last_used_at`）、`PreferenceService.recompute_for_customer`（支付后按近 40 单全量重算，0.85 时间衰减、餐段/周末加权、部分退款降权）、`preference_scene`（季节/天气/同星期/餐段乘子）、`GET /miniprogram/customers/me/preferences`。
- 现状前端：双端 `utils/preferences.js` + 菜单页"智能口味"摘要条 + 加购时按偏好预选规格；无产品级推荐位、无行为埋点、无评价入口。
- 基础设施：Redis（`redis_client.get_redis`，现用于 leader 锁/WS/限流）、APScheduler（`tasks/scheduler.py` leader fence 模式）、Alembic 迁移（最新 0017，MySQL 原生 SQL + 存在性检查风格）、pytest（sqlite 内存 `Base.metadata.create_all`）。
- 数据模型：`Product`（含 `is_recommended/is_hot/sales_count/category_id/status/stock`）、`ProductCategory`（门店数据驱动，面馆可建任意品类）、`OptionGroup/Option/ProductOptionGroup`、`Order/OrderItem/OrderItemOption`（含选项快照与 option_code）。
- 已确认的四个产品决策（2026-09-20 用户拍板）：
  1. 产品口味标签：自动推导 + 后台可微调；
  2. 反馈采集：隐式行为为主 + 订单后轻量标签评价；
  3. 量化指标：A/B + 埋点 + 效果报表框架，离线合成数据验证算法提升；
  4. 隐私：完整合规包（开关 + 查看/清除 + 留存清理 + 同意留痕 + 文案）。
- 历史经验约束：偏好写入须支持"肯定/否定/改口覆盖/互斥/去重"语义，单一事实源持久化于 DB，不得内存态与 DB 态并存。

## Functional Requirements

### A. 数据模型与产品口味画像
- **FR-1**: 新增产品口味画像存储：每个产品一份口味属性（辣度、甜度等可量化维度 + 口感/风味标签集合 + 数据来源 AUTO/MANUAL + 手动覆盖项），后台产品编辑接口可读写；AUTO 重算不得覆盖 MANUAL 覆盖项。
- **FR-2**: 口味画像自动推导：基于产品名、描述、分类名、绑定规格选项（如辣度组、甜度组、温度组、加料）经规则词典推导，产品/分类/规格变更后可重算；词典与规则集中可配置。
- **FR-3**: 后台（Vue 管理端）产品编辑页提供口味标签微调 UI，保存后来源标记为 MANUAL。

### B. 顾客行为采集与画像
- **FR-4**: 双端小程序通过统一埋点工具采集行为事件：推荐位曝光 EXPOSE、产品点击 CLICK、加购 CART_ADD、移除加购 CART_REMOVE、下单 ORDER_PAID（沿用支付链路）、复购 REORDER、评价反馈 FEEDBACK；事件带客户端幂等 ID、场景位（menu/recommend/cart/detail）、A/B 分桶。
- **FR-5**: 后端提供批量事件上报接口（单次最多 50 条），按 event_id 幂等去重；未登录顾客不写入；关闭个性化推荐的顾客事件一律不落库（除"开关操作"审计本身）。
- **FR-6**: 顾客画像新增"品类（CATEGORY）/产品（PRODUCT）/口味标签（TASTE_TAG）"三个维度的统计画像，与现有规格选项偏好并存，互不破坏。
- **FR-7**: 画像更新采用增量学习：事件入库即触发该顾客画像增量更新；另有 ≤5 分钟间隔的批处理任务兜底重算滞留事件；画像带 last_computed_at。
- **FR-8**: 轻量评价：已支付订单的产品可提交一次评价（合口味/偏淡/偏咸/太辣/不够辣/不喜欢等标签，可扩展），负向标签对该产品及相关口味维度产生降权，评价不可重复刷（幂等）。

### C. 产品级推荐
- **FR-9**: 新增推荐服务与 `GET /miniprogram/recommendations`：按当前门店 + 顾客返回产品列表（默认 10 条），仅返回该门店在售（门店库存覆盖 + 品牌状态 + 库存>0）餐品，支持场景参数（recommend_menu / settle_addon）。
- **FR-10**: 三态降级：热启动=内容画像匹配 + 订单共现协同过滤 + 热销 + 场景乘子混合排序；温启动=偏好品类 + 热销补充；冷启动/关闭个性化=门店热销 + is_hot + 新品的非个性化榜单。任何分支必须返回满额可用结果（不足时用热销补齐，永不空列表，除非门店无在售餐品）。
- **FR-11**: 分类差异化：推荐排序中品类权重按分类配置（`ProductCategory.recommend_config` JSON，缺省读全局 system_settings），不同品类可独立调整偏好匹配/协同/热销/新品/复购窗口权重。
- **FR-12**: 负反馈生效：CART_REMOVE、退款、负向评价对对应产品/口味标签降权；同一顾客近期已下单产品按可配置"去重窗口天"降权（窗口可被分类配置覆盖，饮品类窗口短、面类窗口长）。
- **FR-13**: 双端菜单页新增"猜你喜欢"横滑推荐区（口味条下方、菜单主体上方，骨架屏 + 懒加载，不阻塞菜单首屏）；点击与加购与现有产品详情/快捷加购链路复用；推荐位曝光与采纳（点击/加购）必须带场景与分桶上报。
- **FR-14**: 结算页提供"顺手再来一份"搭配推荐（settle_addon 场景，排除已在购物车的产品），同样带埋点。

### D. A/B 实验框架
- **FR-15**: 实验配置（后端管理 API + Vue 页面）：实验 key、名称、状态（草稿/运行/暂停）、流量比例、桶名与对应策略参数（如 reco_algo=v1/v2）；顾客按稳定哈希分桶，同一顾客在同一实验内桶位恒定，未命中实验走默认桶。
- **FR-16**: 推荐接口响应头/响应体返回命中的实验桶；曝光、点击、加购、下单事件携带桶标记。
- **FR-17**: 后台推荐效果报表：按实验/桶/时间范围聚合曝光数、点击数、点击率 CTR、加购采纳率（推荐位产生加购数/曝光数）、推荐位下单转化率、人均推荐 GMV；数据来自行为事件聚合，支持离线查询。

### E. 性能优化
- **FR-18**: 响应耗时中间件：为所有 /api 请求记录耗时，按路由模板聚合 P50/P95/P99 与 QPS 到 Redis（滚动时间窗），慢请求（>800ms）写结构化日志；管理端提供只读性能指标查询接口。
- **FR-19**: Redis 缓存层：①门店菜单/分类聚合结果按 store_id 缓存，产品/分类/规格/门店库存变更时主动失效；②顾客推荐结果按 (customer, store, scene, bucket) 短 TTL（≤120s）缓存，画像更新/下单后主动失效本人缓存；③缓存不可用时自动直查数据库，功能不报错。
- **FR-20**: 启用 GZip 中间件（仅压缩大于阈值的 JSON 文本响应，图片/已压缩内容跳过）。
- **FR-21**: 前端性能：菜单数据与产品目录增加 storage 缓存 + 版本号/轻量校验（后端支持版本戳，无变化走 304/Not Modified 语义的轻响应）；推荐区异步加载不阻塞首屏；图片继续懒加载；双端埋点合并为单次批量请求并在页面 onHide/退后台时 flush。
- **FR-22**: 接口瘦身：推荐接口仅返回列表渲染必需字段（id/name/price/图片/标签/理由/价格活动标记），不返回全量 option_groups 等重字段。

### F. 隐私合规
- **FR-23**: 顾客可在小程序会员/设置区开关"个性化推荐"；关闭后推荐接口退化为非个性化热销榜，行为事件不再采集，画像增量更新停止；重新开启后可基于历史订单恢复画像。
- **FR-24**: 提供"查看我的口味画像"（只读展示各维度画像）与"清除口味画像"（删除行为事件、评价画像派生数据与偏好；订单法定数据不删，仅解除关联用于推荐）接口与前端入口，清除动作留审计日志。
- **FR-25**: 行为事件按可配置留存期（默认 90 天）由定时任务自动清理/匿名化。
- **FR-26**: 个性化推荐与埋点的启用状态在首次使用时经现有隐私弹窗体系取得同意并记录（顾客级、版本化、时间戳）；隐私文案提供"个性化推荐与口味画像说明"段落。

## Non-Functional Requirements
- **NFR-1 性能**: 推荐接口与菜单聚合接口在缓存命中时服务端 P95 ≤ 100ms、缓存未命中（预热态）P95 ≤ 500ms（测试环境单用户、门店餐品 ≤500 SKU 条件下）；管理端可查近 24h 路由 P95。
- **NFR-2 性能目标**: 推荐接口平均响应耗时相对"无缓存直查 DB"基线下降 ≥ 40%（基准脚本/离线报告给出同机前后对比证据）。
- **NFR-3 实时性**: 从顾客产生行为事件到其画像 last_computed_at 推进，延迟 ≤ 5 分钟（增量路径秒级，兜底任务周期 ≤ 5 分钟）。
- **NFR-4 算法效果**: 合成数据集（≥500 顾客、≥2000 订单、≥100 SKU、多品类、含噪声与负反馈）离线评估，新算法相对现有基线 precision@5 ≥ +30%、推荐采纳代理指标（点击+加购命中率）≥ +25%，评估脚本可重复运行并输出报告。
- **NFR-5 可靠性**: Redis 不可用、天气等外部依赖失败时推荐链路降级而非报错；埋点上报失败不得影响点餐主流程（静默失败、本地重试一次）。
- **NFR-6 兼容性**: 现有规格偏好接口、智能口味条、加购预选逻辑行为不退化；新增表必须有 Alembic 0018 迁移（MySQL）且测试库 create_all 可用；双端微信/支付宝功能与接口语义一致。
- **NFR-7 安全**: 所有新接口遵循现有顾客 JWT 鉴权；埋点接口防刷（沿用限流中间件）、入参白名单校验；管理端接口需要对应权限；顾客只能读写本人画像/评价数据（越权访问返回 403）。
- **NFR-8 可观测**: 推荐链路关键节点（分桶、召回数量、耗时、缓存命中）有结构化日志；效果与性能指标可在后台查看。
- **NFR-9 测试**: 新增后端逻辑 pytest 覆盖核心规则（画像增量、三态推荐、负反馈、分桶幂等、缓存失效、隐私开关、留存清理），全量回归通过；前端改动文件通过 node --check 语法校验。

## Constraints
- **Technical**: 后端 FastAPI + SQLAlchemy async + MySQL（生产）/SQLite（测试）；仅可使用 requirements.txt 已有依赖（redis、apscheduler、numpy 若需须先确认；优先纯 Python 实现，避免新增重依赖）。
- **Technical**: 双端小程序原生 JS（无 npm 构建链），所有工具代码须同时在微信 `wx.*` 与支付宝 `my.*` API 下工作，沿用现有双文件同构模式。
- **Technical**: 数据库迁移须沿用 `backend/alembic/versions` 的 MySQL 原生 SQL + 存在性检查风格，编号 0018；测试不跑迁移而靠模型 create_all。
- **Business**: 面馆为正餐扫码点餐场景，推荐位不得遮挡点餐主流程，不得自动加购；推荐理由文案须可解释（如"您常点·辣度更高""本桌热销"）。
- **Dependencies**: 上线真实指标提升依赖线上 A/B 实验运行 ≥2 周的真实流量；离线指标依赖合成数据生成器。
- **Process**: 测试代码只能放 `e:\SmartNoodleHouse\tests`；不新建无关文档；所有思考与回复使用简体中文；PowerShell 命令用 `;` 分隔。

## Assumptions
- 静默登录已保证每个小程序顾客有 customer_id（现有链路已实现），行为事件均可关联顾客。
- 门店餐品规模单店 ≤500 SKU，订单共现矩阵按门店在 Redis/进程内计算可行；超规模时以热销降级。
- 现有 `sales_count` 与 is_hot 数据可作为冷启动热销来源。
- 现有隐私弹窗（privacy popup）具备可扩展的同意项机制；若无则在其配置中新增条目。
- 顾客"注销/删除账号"的匿名化链路（customer_merge / PII 清理）扩展时只需挂接事件清理。

## Acceptance Criteria

### AC-1: 行为事件批量采集与幂等
- **Type**: `rule`
- **Given**: 已登录顾客在小程序产生点击、加购、曝光等行为
- **When**: 客户端批量（≤50 条）调用事件上报接口，且重复发送含相同 event_id 的事件
- **Then**: 首次全部入库，重复 event_id 不产生重复记录；非法 event_type/超长字段被拒绝（4xx）且不影响其他事件；接口返回成功条数
- **Pass Condition**: pytest 验证幂等去重、批量上限、字段白名单全部通过
- **Evidence**: `tests/` 新增推荐系统测试报告 + 接口实现代码行号

### AC-2: 产品口味画像自动推导与手动覆盖
- **Type**: `rule`
- **Given**: 门店存在绑定"辣度/甜度/温度"等规格组、名称含口味词的产品
- **When**: 触发画像推导（产品保存后或批量重算），随后店长在后台修改部分标签
- **Then**: 自动画像按词典规则生成；手动项被标记 MANUAL；再次自动重算不覆盖手动项；后台接口可读写且管理端 UI 可保存
- **Pass Condition**: pytest 覆盖推导规则、MANUAL 不被覆盖、接口鉴权；前端页面存在且可提交（代码+构建证据）
- **Evidence**: 测试输出 + 后台产品编辑页代码路径

### AC-3: 推荐接口三态降级与门店隔离
- **Type**: `rule`
- **Given**: 分别构造无任何行为顾客、少量行为顾客、丰富画像顾客，以及两门店各自餐品
- **When**: 调用 `GET /miniprogram/recommendations?store_id=X&scene=recommend_menu`
- **Then**: 三态顾客分别获得热销榜/偏好+热销/个性化混合排序结果；结果只含该门店在售且有库存餐品；数量不足时用热销补齐；关闭个性化的顾客恒得非个性化结果且结果可稳定复现
- **Pass Condition**: pytest 三态 + 跨店隔离 + 关闭开关 + 空店不报错全部通过
- **Evidence**: 测试用例与断言

### AC-4: 画像增量学习 ≤5 分钟
- **Type**: `rule`
- **Given**: 顾客产生一条加购/点击事件
- **When**: 事件上报成功
- **Then**: 增量更新立即推进该顾客画像 last_computed_at；模拟增量失败时，兜底任务在 ≤5 分钟周期内重算滞留事件
- **Pass Condition**: pytest 验证事件后画像变化（直接路径）与兜底任务补偿路径；scheduler 注册项周期 ≤300s
- **Evidence**: 测试输出 + scheduler 注册代码

### AC-5: 轻量评价负反馈影响排序
